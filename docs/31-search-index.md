# 31 · 검색 — 색인 · 방식 · 정규식 가속 (2026-09-04)

> 사용자(09-04): *"nexa-app을 치면 터미널 복사본이 빠진다 — 기준이 뭐냐 · 정규식도 선택하게 · 일반 검색도 본문 전체 ·
> **본문이 blob 파일에 흩어져 있으니 I/O 병목 조치** · 정규식에도 쓰이는 자료 구조."*
> 구현: [`nclip_core::search`](../crates/nclip-core/src/search.rs) · [`search_index`](../crates/nexa-clip/src/search_index.rs) · 설정 [14 §3-8](14-settings-registry.md#3-8-검색-search) · 실기 [21 §9](21-manual-test.md).

## 1. 종전 기준과 문제

메인·팝업 모두 **라벨(첫 줄 44자)** 에 질의가 부분 문자열로 들어 있는지만 봤다. 둘째 줄 이후에만 있는 말은 못 찾았고,
설정 `find.mode`(정확히/유사/정규식)는 코드가 읽지 않았다. 게다가 16KB 이상 본문은 blob(지연 로드)이라 RAM에 없어
검색은커녕 미리보기에도 안 보였다.

## 2. 구조 — 한 자료 구조가 세 방식을 다 받는다

```
HistoryItem(메타 · 상주)                 search_index: HashMap<id, Rc<str>>      Matcher(find.mode)
  ├ label ─────────────────────┐          ┌──────────────────────────────┐        ├ Exact  : contains(needle)
  ├ reps(text · inline)  ──────┼─ 소문자 ─▶│ "라벨
본문…"(≤256KB · 소문자) │◀─ 훑기 ─┤ Fuzzy  : 모든 단어 contains
  └ blob_refs(text · ≥16KB) ───┘ 배경 스레드 └──────────────────────────────┘        └ Regex  : 자체 엔진 is_match
                                (BlobReader 한 번)
```

| 원칙 | 구현 |
| --- | --- |
| **검색 때 파일 I/O 0** | 색인은 RAM. 기동 때 미적재 텍스트 blob만 배경 스레드(`BlobReader` = 경로 + 키만 든 `Send` 손잡이)가 **한 번** 읽어 `SearchText` 이벤트로 채운다. 그동안은 라벨로 걸러진다(점진 · UI 무정지 · DR-41) |
| **소문자 변환 0** | 색인 자체가 소문자. `Matcher::matches_lower`가 그대로 훑는다 |
| **한 구조 · 세 방식** | 정확히·유사·정규식 모두 같은 검색문을 본다 — 정규식도 색인 위에서 돈다 |
| **상한** | 항목당 256KB(문자 경계 절단) · 1만 건이라도 수십 MB 안 |
| **동기** | 캡처·수신·편집 = 즉시 갱신(손에 있는 본문) · 삭제·일괄 삭제 = 제거 · `find.mode` 변경 = 다음 박동에 열린 창 재필터 |

## 3. 자체 정규식 엔진(DR-8 — 외부 crate 0)

백트래킹 · 지원 = 리터럴 · `.` · `* + ?` · `{n} {n,} {n,m}` · `[abc] [a-z] [^…]` · `\d \w \s \D \W \S ` · `^ $` · `( … | … )` · `(?:…)`.
게으른 `*?`는 탐욕과 같이 취급(부분 일치 판정에는 차이 없음). 컴파일 실패 → **정확히**로 폴백(`Matcher::error`).
폭주 방어 = 매칭 단계 20만 회 상한(`(a+)+$` 같은 패턴도 UI를 잡지 못한다) · 패턴 256자 · 괄호 깊이 16.

## 4. 규모가 커지면 — 정규식까지 가속하는 층 (설계 · 실측 뒤 착수)

지금(수백 건)은 항목당 `contains`/`is_match`가 μs~ms라 색인만으로 충분하다. **5천 건 · 수십 MB**를 넘으면 아래를 올린다.
핵심은 **정규식도 같은 후보 좁히기를 탄다**는 것(사용자 09-04 "정규식에도 반영되는 자료 구조").

| 층 | 내용 | 정규식에 쓰는 법 |
| --- | --- | --- |
| **삼중자(trigram) 포스팅** | 검색문의 모든 3글자 조각 → 항목 id 집합(`HashMap<[char;3], Vec<u64>>` · 증분 갱신) | 정규식 AST에서 **필수 리터럴**을 뽑는다(연접의 리터럴 연속 · 그룹/선택은 공통 접두·접미 · `?`/`*`는 버림). 예: `nexa[-_]app\.exe$` → `nexa` · `app.exe` → 두 리터럴의 삼중자 교집합이 후보 · 후보에만 엔진을 돌린다(Google Code Search · ripgrep 방식) |
| **증분 좁히기** | 질의가 직전 질의의 확장(`nexa` → `nexa-`)이면 직전 결과만 다시 본다 | 정규식은 확장 판정이 안 되므로 삼중자 층만 |
| **입력 코얼레싱** | 키 입력 70ms 의도(28 §hover의 `HoverIntent` 그대로) 뒤 1회 필터 | 공통 |
| **하이라이트** | 일치 구간 `(start, end)`를 `Matcher`가 돌려주면 행에 강조 — 엔진이 위치를 이미 안다 | 공통 |

착수 조건: 항목 5천 건 이상에서 키 입력 1회 필터가 16ms를 넘는 실측이 나올 때. 그 전엔 낭비(DR-41).
