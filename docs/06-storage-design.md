# 06 · 저장 설계 — DB인가 파일 직렬화인가 (D-1 답)

> **질문(사용자 2026-08-25)**: *"클립보드는 무제한 혹은 제한된 숫자 범위에서 저장해두고 계속 사용하는 방식인데, 간단하게라도 DB화 시키는 게 좋을까? 아니면 파일로 Serializing 하는 걸로 충분할까?"*
>
> **결론**: ★ **파일 직렬화로 충분하다. 단 "그냥 파일"이 아니라 세 가지를 지켜야 한다** —
> **① 인덱스와 blob 분리 · ② append-only + 세그먼트 · ③ 내용 주소 blob**.
> 이 셋을 지키면 우리가 필요한 DB 성질(빠른 조회·중복 제거·손상 복원·삭제)이 전부 나오고,
> **SQLite를 넣었을 때 잃는 것**([§3](#3-왜-sqlite가-아닌가))을 치르지 않는다.
>
> 작성 2026-08-25 · [04 §5 D-1](04-feature-scope-and-screens.md#5-열려-있는-결정-adr-후보)의 답.

---

## 1. 먼저 — 우리의 접근 패턴은 실제로 무엇인가

설계를 고르기 전에 **이 앱이 저장소에 무엇을 시키는지** 세어 본다. 여기가 답을 결정한다.

| # | 동작 | 빈도 | 성격 |
|---|---|---|---|
| **A-1** | 새 항목 추가 | 복사할 때마다(하루 수백 회) | ★ **append** — 중간 수정 없음 |
| **A-2** | 최근 N개 목록 표시 | 팝업 열 때마다 | ★ **시간 역순 앞쪽 100개** — 항상 같은 모양 |
| **A-3** | 부분 문자열 검색 | 타이핑 한 글자마다 | ★ **전체 스캔** — 16ms 안에 끝나야 함 |
| **A-4** | 항목 1개 상세 읽기 | 선택할 때 | 단건 조회 |
| **A-5** | 정책 만료 삭제 | 주기적(하루 몇 회) | ★ **오래된 쪽 통째로** — 개별 삭제 아님 |
| **A-6** | 수동 삭제 · 고정 토글 | 가끔 | 단건 갱신 |

> ★ **관찰**: 우리에게 **join이 없고, 트랜잭션 경합이 없고, 복잡한 질의가 없다.**
> 쓰기는 **끝에 붙이기**, 삭제는 **앞에서 자르기**, 검색은 **훑기**다.
> 이건 **DB가 잘하는 문제가 아니라 로그가 잘하는 문제**다.

## 2. 권장 구조 — "파일이되 DB처럼"

```
data/
├─ index/                     ← 작다. 메모리에 올린다
│  ├─ seg-000042.idx          ← append-only 세그먼트(봉인 · AEAD)
│  ├─ seg-000043.idx          ← 현재 쓰는 중
│  └─ manifest                ← 세그먼트 목록 · 세대 · 체크섬
├─ blob/                      ← 크다. 필요할 때만 읽는다
│  ├─ 3f/3fa9c1…              ← 내용 주소: blob_id = H(암호문)
│  └─ 7b/7b02e4…
└─ keys                       ← 래핑된 마스터 키(ADR-0005 계층)
```

### 2-1. 인덱스 레코드 — 작게 유지하는 것이 전부

| 필드 | 크기 | 비고 |
|---|---:|---|
| `item_id` | 16B | |
| `blob_id` | 32B | 본문은 여기 없다 — **참조만** |
| 타입 · 플래그(고정·민감) | 2B | |
| 생성 시각 · 바이트 크기 | 16B | |
| 출처 앱 id · 그룹 id | 4B | 문자열이 아니라 **id**(문자열은 별도 사전) |
| **미리보기 텍스트** | ~200B | ★ 목록 표시용으로 **잘라서** 넣는다 |
| **합계** | **≈ 270B / 항목** | |

**메모리 실측 추정**

| 항목 수 | 인덱스 RSS | 판정 |
|---:|---:|---|
| 1,000 | ~0.3MB | 여유 |
| 10,000 | **~2.7MB** | ★ 기본값 권장 구간 |
| 50,000 | ~13MB | 가능하나 예산 압박 |
| 100,000 | **~27MB** | ⚠️ 유휴 RSS 예산([04 §0 ④](04-feature-scope-and-screens.md#0-제품-한-줄과-설계-축))을 혼자 다 먹는다 |

> 👉 **기본 상한 5,000~10,000이면 인덱스 전체를 메모리에 상주**시킬 수 있고,
> 그러면 **A-3 검색이 그냥 메모리 순회**가 된다. 1만 건 부분 문자열 매칭은 **1ms 미만** — 16ms 예산 안에서 논쟁거리가 아니다.
> ★ **검색 색인(FTS)이 필요 없어지는 이유가 이것이다.**

### 2-2. append-only + 세그먼트 — 삭제와 손상을 동시에 푼다

| 문제 | 해법 |
|---|---|
| **A-5 정책 만료** | 오래된 **세그먼트 파일을 통째로 지운다.** 레코드 단위 삭제·조각 모음이 없다 |
| **A-6 단건 삭제** | 묘비(tombstone) 레코드를 append. 컴팩션 때 실제로 사라진다 |
| **손상 복원력** | 레코드마다 길이 + 체크섬. 꼬리가 깨지면 **마지막 레코드만 버리고 나머지는 산다** |
| **원자성** | 새 세그먼트에 쓰고 `manifest` 교체(원자적 rename). 중간에 죽어도 이전 상태가 온전 |

> ★ **이건 beep이 이미 쓰는 모양이다** — `nbeep-store`의 **암호화 세그먼트**(AEAD · 논스 base+seq · AAD 인증).
> 재발명이 아니라 **이식**이다.

### 2-3. 내용 주소 blob — 중복 제거가 공짜로 온다

`blob_id = H(암호문)` 로 잡으면:

| 얻는 것 | 내용 |
|---|---|
| ★ **중복 제거** | **클립보드는 같은 것을 반복 복사하는 도구다.** 같은 내용이면 blob_id가 같아 **파일이 하나만 남는다** |
| 변조 탐지 | 내용이 바뀌면 주소가 안 맞는다 |
| ★ **동기화와 정합** | [05 §4](05-multi-device-sharing.md#4--클립보드에-특히-잘-맞는-구조--blob-1개--봉투-n개)의 blob 구조와 **같은 식별자** — 로컬 저장과 기기 간 전송이 하나의 개념을 공유한다 |

> 👉 [04 FR-C-10](04-feature-scope-and-screens.md#1-1-캡처-fr-c--클립보드에서-우리-쪽으로)(중복 감지)이 여기서 **저장 공간 절약**으로, [05](05-multi-device-sharing.md)에서 **업로드 생략**으로 — **한 규칙이 세 곳에서 배당금을 낸다.**

## 3. 왜 SQLite가 아닌가

> ⚠️ **공정하게 말하면 SQLite는 이 문제의 표준 답이고, 경쟁 제품이 거의 다 그걸 쓴다** —
> **Ditto**(SQLite) · **EcoPaste**(SQLite + FTS5) · **Maccy**(Core Data = SQLite).
> 그럼에도 우리는 안 쓴다. 이유는 넷이고, **그중 둘은 우리 결정 때문에 생긴 것**이다.

| # | 이유 | 무게 |
|---|---|---|
| **①** | ★ **암호화가 SQLite의 강점을 무력화한다.** [05 §5 D-9](05-multi-device-sharing.md#6-열린-결정)대로 디스크를 봉인하면 **암호문에는 인덱스도 FTS도 걸 수 없다.** SQLite를 넣고도 검색은 결국 복호 후 스캔이다 → **DB를 쓰면서 DB의 이점을 못 쓴다** | ★★ 결정적 |
| **②** | **외부 crate 0 지향(DR-8 계승).** `rusqlite`는 C 라이브러리를 번들한다 — 바이너리 크기·빌드 복잡도·5타깃 크로스 컴파일 부담. **SQLCipher는 라이선스 문제**(퍼미시브 온리 원칙과 충돌) | ★★ |
| **③** | **질의가 단순하다.** [§1](#1-먼저--우리의-접근-패턴은-실제로-무엇인가)에 join도 트랜잭션 경합도 없다. **SQL을 쓸 일이 없는데 SQL 엔진을 링크한다** | ★ |
| **④** | **선례가 있다.** beep `nbeep-store`의 암호화 세그먼트를 이식하면 **새로 설계할 것이 거의 없다** | ★ |

### 3-1. 반대로 — SQLite가 옳아지는 조건

정직하게 적어 둔다. **아래에 해당하면 이 결정을 뒤집어야 한다.**

| 조건 | 지금 판단 |
|---|---|
| 항목이 **10만 개를 상시로 넘긴다** | 기본 상한이 5,000~10,000이면 도달하지 않는다. **"무제한" 옵션을 켠 사용자만** 문제 → [§4](#4-무제한을-어떻게-다루나) |
| **복합 질의**가 필요하다(태그 AND 출처 AND 기간 AND 전문) | 현재 FR에 없다. 생기면 재검토 |
| 다중 프로세스 동시 쓰기 | 우리는 단일 상주 프로세스다 |
| 암호화를 포기한다 | 그러면 SQLite+FTS5가 더 낫다. **하지만 [05 §5](05-multi-device-sharing.md#5-사용자-방향에-대한-검토--전송은-봉인-로컬은-해제)에서 CopyQ보다 후퇴한다는 결론이 나왔다** |

## 4. "무제한"을 어떻게 다루나

사용자 질문에 **"무제한 혹은 제한된 숫자 범위"** 가 같이 있었다. 이 둘은 **저장 구조가 갈리는 지점**이라 나눠 둔다.

| 모드 | 인덱스 | 검색 | 비고 |
|---|---|---|---|
| **제한(기본 · 권장)** ≤ 1만 | **전체 메모리 상주** | 메모리 순회 — **즉시** | ★ [§2-1](#2-1-인덱스-레코드--작게-유지하는-것이-전부) 그대로 |
| **대용량** 1만~10만 | 최근 세그먼트만 상주 | 최근은 즉시, 과거는 **백그라운드 워커가 세그먼트 순차 복호 스캔**(진행률 표시) | 팝업 응답성은 유지된다 |
| **무제한** | 동일 + 세그먼트 무한 증가 | 위와 같되 시간이 늘어난다 | ⚠️ **디스크는 유한하다** — 진짜 무제한은 없다 |

> ★ **권고**: "무제한"을 **개수 무제한이 아니라 "용량 상한으로만 관리"** 로 제공한다.
> 사용자에게는 *"5GB까지 보관"* 이 *"무제한"* 보다 정직하고, 우리에게는 세그먼트 회수 기준이 명확해진다.
> [04 FR-H-2](04-feature-scope-and-screens.md#1-2-보관-fr-h)가 **개수·기간·용량 셋 다** 제공하기로 한 것과 맞물린다.

## 5. 결정 (D-1 답 · 확정 대기)

| # | 내용 |
|---|---|
| **D-1-a** | ★ **자체 파일 직렬화를 채택한다.** SQLite 등 DB 엔진은 링크하지 않는다 |
| **D-1-b** | **인덱스(작음·메모리 상주) / blob(큼·내용 주소 파일)** 을 분리한다 |
| **D-1-c** | 인덱스는 **append-only 암호화 세그먼트 + manifest** — beep `nbeep-store` 이식 |
| **D-1-d** | `blob_id = H(암호문)` — **중복 제거와 [05](05-multi-device-sharing.md) 동기화가 같은 식별자를 공유** |
| **D-1-e** | 기본 상한 **1만 항목** 권장. 그 이상은 세그먼트 페이징으로 열되 **검색 지연을 UI에 표시** |
| **D-1-f** | ★ **저장 계층을 트레이트 뒤에 둔다** — [§3-1](#3-1-반대로--sqlite가-옳아지는-조건)의 조건이 실제로 오면 **교체가 가능하도록**. 지금 재발명하지 않기 위한 보험이 아니라, **틀렸을 때 되돌리기 위한 보험** |

> 🔴 **사용자 확정 필요.** 확정되면 [04 §5](04-feature-scope-and-screens.md#5-열려-있는-결정-adr-후보)의 D-1을 닫고 DR 표에 옮긴다.
