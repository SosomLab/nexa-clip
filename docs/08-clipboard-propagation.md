# 08 · 클립보드 자동 전파 — 무엇이, 언제, 어디까지 흐르나

> **사용자 요구(2026-08-25)**: *"연결이 되었다는 전제하에서, 한쪽 PC에서 클립보드/파일(내용이 아닌 목록)/텍스트 등을 복사하면 해당 내용이 다른 PC로(동일 네트워크 및 원격 포함) 자동 전파되어 붙여넣기를 할 수 있는 상태로 기능 제공."*
>
> **결론**: 구조적으로 성립한다([05](05-multi-device-sharing.md)·[07](07-device-rendezvous.md)이 전송·신원을 이미 덮는다).
> 남는 것은 **전파 의미론(semantics)** 이고, 여기에 **반드시 먼저 답해야 하는 함정 셋**이 있다 —
> ★ **① 파일 목록은 상대 PC에서 깨진다**([§3](#3--함정--파일-목록은-상대-pc에서-깨진다)) ·
> ★ **② 자동 덮어쓰기는 상대의 작업을 파괴한다**([§4](#4--함정--자동-덮어쓰기는-상대의-작업을-파괴한다)) ·
> ★ **③ 에코 루프**([§5](#5--함정--에코-루프-무한-왕복)).
>
> 작성 2026-08-25.

## 3. ⚠️ 함정 — 파일 목록은 상대 PC에서 **깨진다**

`D:\작업\보고서.xlsx` 를 A에서 복사해 B로 전파하면, **B에는 그 경로가 없다.** B의 탐색기에 붙여넣으면 *"경로를 찾을 수 없습니다"* 가 뜨거나 **아무 일도 일어나지 않는다.**

> ★ **이건 구현 버그가 아니라 요구 자체에 내재한 성질**이다. 먼저 결정해야 한다.

### 3-1. 선택지

| 안 | 대상 PC 클립보드에 올리는 것 | 결과 |
|:--:|---|---|
| **가** | **파일 객체**(`CF_HDROP` 등) 그대로 | ⚠️ 경로가 없으면 **조용히 실패** — 최악의 UX |
| **나** | ★ **텍스트(경로 문자열)로만** | 항상 성공. 파일로는 못 쓰지만 **경로 공유로는 유용** |
| **다** | ★ **경로가 실재하면 파일 객체, 아니면 텍스트** | 상황 적응 — **네트워크 드라이브·동일 경로 구조에서 그대로 동작** |
| **라** | 요구 시 내용 가져오기(on-demand) | 강력하나 *"내용이 아닌 목록"* 이라는 확정 범위를 넘는다 → 2차 |

### 3-2. 권장 — **다(적응형) + 목록 UI에 상태 표시**

```
📁 3개 파일                          A-데스크톱 · 방금
   D:\작업\보고서.xlsx  ⚠ 이 PC에 없음
   \\nas\공유\사양서.pdf  ✅ 접근 가능
   D:\작업\초안.md      ⚠ 이 PC에 없음
```

| 규칙 | 내용 |
|---|---|
| **P-1** | 붙여넣기 직전에 **각 경로의 실재를 확인**한다 |
| **P-2** | **전부 실재** → 파일 객체로 올린다(원래 의도대로 동작) |
| **P-3** | **일부/전부 부재** → **텍스트(경로 목록)로 올린다** + 팝업에 *"파일로는 붙여넣을 수 없습니다"* 표시 |
| **P-4** | ★ **조용히 실패하지 않는다** — 어느 쪽으로 올렸는지 항상 보인다 |
| **P-5**(2차) | UNC·매핑 드라이브 대응 — `Z:\` ↔ `\\nas\공유` 변환 규칙을 사용자가 등록 |

> 👉 **NAS·공유 폴더를 함께 쓰는 환경에서는 "다"가 그대로 완전한 파일 전파처럼 동작한다.**
> 그렇지 않은 환경에서도 **경로 목록 공유**라는 실질적 가치가 남는다.

## 4. ⚠️ 함정 — 자동 덮어쓰기는 **상대의 작업을 파괴한다**

*"붙여넣기를 할 수 있는 상태"* = 대상 PC의 **시스템 클립보드를 덮어쓴다**는 뜻이다. 그런데 그 순간 B의 사용자가 **다른 것을 복사해 붙여넣으려던 중**이면, **그 사람의 클립보드가 예고 없이 바뀐다.**

> ★ 이건 다중 기기 클립보드 제품에서 **사용자를 가장 화나게 하는 1순위**다.
> 하필 클립보드는 **"방금 복사한 것"에 대한 신뢰**로 돌아가는 도구다.

### 4-1. 세 가지 모드 — 사용자가 고른다

> ★ **확정([DR-28](10-decision-record.md) 08-26)**: **내 기기끼리(같은 `UserId` · 상호 신뢰)는 ②가 기본**이다 —
> *"승인 과정 없이 한쪽이 먼저 전송하고 수신측은 바로 시스템 클립보드에 반영 및 알림"*.
> ⚠️ **다른 `UserId`와의 공유는 승인을 유지**한다([05 §6-2-1](05-multi-device-sharing.md#6-2-1--클립보드-보내기send--프로토콜-사용자-확정-2026-08-26) DR-22) — 축이 다르다.

| 모드 | 동작 | 적합 |
|---|---|---|
| ★ **② 자동 덮어쓰기**(**내 기기 기본값**) | 받는 즉시 시스템 클립보드에 올리고 **알림**한다 | ✅ **DR-28** — 기기 경계가 안 느껴지는 것이 목적이다 |
| **① 기록만** | 시스템 클립보드는 **안 건드리고** 기록 맨 위에만 넣는다 | 두 PC를 **동시에 집중해서** 쓰는 사람의 선택지 |
| **③ 유휴일 때만 덮어쓰기** | 대상 PC가 유휴면 덮어쓰고, 사용 중이면 ①로 | 절충 — 두 상황 자동 판별 |

### 4-2. 어느 모드든 지키는 것

| 규칙 | 내용 |
|---|---|
| **W-1** | ★ **덮어쓰기 전 대상 PC의 현재 클립보드를 기록에 먼저 저장**한다 → **잃는 것이 없다**. **승인을 없앤 대신 이것이 안전장치다**(DR-28) |
| **W-2** | ★ **덮어쓰면 반드시 알린다**(토스트) — *"A-데스크톱에서 받음 · ⌘Z로 되돌리기"*. 사용자 확정 요구(DR-28) |
| **W-3** | ★ **되돌리기 제공** — 직전 클립보드로 복원 |
| **W-4** | 민감·제외 규칙은 **보낼 때와 받을 때 두 번** 검사(fail-closed) |

> **W-1 하나가 ②의 위험을 대부분 없앤다** — 덮어써도 **원래 것이 기록 맨 위 두 번째에 그대로 있다.**

## 5. ⚠️ 함정 — 에코 루프 (무한 왕복)

```
A에서 복사 → B로 전파 → B가 클립보드에 씀 → B의 감시가 "새 복사"로 감지
          → A로 전파 → A가 클립보드에 씀 → A의 감시가 감지 → …
```

**자동 전파 + 클립보드 감시가 있으면 반드시 발생한다.** 방어는 선택이 아니다.

| 규칙 | 내용 |
|---|---|
| **E-1** | 모든 항목에 **`origin`(최초 기기 id) + `item_id`** 를 붙인다. **자기가 만든 것이 아닌 항목은 다시 전파하지 않는다** |
| **E-2** | 클립보드에 **우리가 쓰는 직전**에 그 내용의 해시를 **억제 목록**에 넣고, 감시가 같은 해시를 보면 **새 항목으로 만들지 않는다** |
| **E-3** | 억제 목록은 **짧은 수명**(수 초) + 소량 — 사용자가 같은 것을 진짜로 다시 복사하는 경우를 영원히 막으면 안 된다 |
| **E-4** | `blob_id = H(암호문)` 중복 규칙([06 §2-3](06-storage-design.md#2-3-내용-주소-blob--중복-제거가-공짜로-온다))이 **최후 방어선**으로 한 번 더 걸린다 |

> ★ **E-1이 본체, E-2는 보험이다.** OS 클립보드는 우리가 쓴 것과 사용자가 쓴 것을 구별해 주지 않으므로 **둘 다 필요하다.**

## 6. LAN과 원격을 다르게 다룬다

사용자 요구는 *"동일 네트워크 및 원격 포함"* 이다. **둘을 같은 정책으로 다루면 원격에서 회선이 탄다.**

| | **같은 LAN** | **원격(릴레이)** |
|---|---|---|
| 텍스트·색상·URL | ★ **즉시 전문 전파** | ★ **즉시 전문 전파**(작다) |
| 파일 경로 목록 | 즉시 전문 | 즉시 전문(작다) |
| **이미지** | ★ **즉시 전문 전파** | ⚠️ **메타 먼저**(썸네일·크기) + **붙여넣을 때 본문 가져오기** |
| 대용량 텍스트(> 상한) | 즉시 | 메타 먼저 |

### 6-1. 지연 가져오기(lazy fetch)의 UI

원격에서 메타만 온 항목은 목록에 **바로 보인다.** 선택하는 순간 본문을 가져온다.

```
🖼 스크린샷 1920×1080  ☁         A-데스크톱 · 방금
   └ Enter → "받는 중… 1.2MB / 4.8MB"  (취소 가능)
```

| 규칙 | 내용 |
|---|---|
| **L-1** | 메타 항목도 **목록에 즉시 나타난다** — 사용자는 "있다"는 걸 바로 안다 |
| **L-2** | 가져오는 동안 **진행률 + 취소** |
| **L-3** | 원본 기기가 꺼지면 **정직하게 "원본 기기 오프라인"** 표시([07 §4-1](07-device-rendezvous.md#4-1-️-릴레이는-버퍼가-아니라-파이프다) — 릴레이는 파이프다) |
| **L-4** | 가져온 뒤에는 로컬 blob으로 승격 — 다시 안 가져온다 |

> ★ **`blob_id` 내용 주소가 여기서 또 이득을 준다** — 이미 가진 blob이면 **가져오기 자체가 생략**된다([06 §2-3](06-storage-design.md#2-3-내용-주소-blob--중복-제거가-공짜로-온다)).

## 7. 순서와 충돌

클립보드는 **"가장 최근 것"** 이 지배하는 자료구조라, 동시 복사에서 순서가 갈리면 사용자가 즉시 알아챈다.

| 문제 | 처방 |
|---|---|
| A와 B가 **거의 동시에** 복사 | 항목에 **(기기 논리 시계, 기기 id)** 를 실어 **결정적 전순서**를 만든다. 벽시계만 쓰면 시계 어긋남으로 순서가 뒤집힌다 |
| 목록 표시 | **각 기기의 로컬 도착 순서**가 아니라 **전순서**로 정렬 — 두 PC에서 목록이 같아 보인다 |
| "지금 클립보드" 승자 | ★ **마지막 승자(LWW)** — 클립보드의 자연스러운 의미와 일치한다 |
| 재연결 후 밀린 항목 | **최근 N개만** 따라잡는다. 전부 재생하면 클립보드가 요동친다 |

## 8. 전파 범위 — 무엇을 보낼지 사용자가 정한다

[04 FR-H-2](04-feature-scope-and-screens.md#1-2-보관-fr-h)의 보관 정책과 별개로, **전파 정책**이 따로 필요하다.

| 설정 | 기본값 |
|---|---|
| 전파할 타입 | 텍스트·이미지·파일목록 (전부 켬) |
| **전파 크기 상한** | 원격 = 메타 전환 임계값(예: 1MB) |
| 전파 대상 기기 | 내 기기 전부(자동) — [05 §6-1](05-multi-device-sharing.md#6-1--내-기기--자동-연동) |
| **일시 정지** | ★ **트레이에서 한 번에 끄기**(회의·화면 공유 중) |
| 민감·제외 | 항상 적용(끌 수 없음) |

## 9. 모바일 수신 (Android · iOS) — **최하순위 목표** (사용자 확정 2026-08-25)

> **사용자 확정**: *"Android와 iOS에서도 클립보드를 전달받을 수 있도록 개발 목표에 포함(최하순위)."*
>
> ★ **"전달받는다"로 한정한 것이 정확하다** — 모바일에서 **보내는 쪽(자동 캡처)은 OS가 사실상 막아 놨고**, **받는 쪽은 가능**하다. 요구가 이미 실현 가능한 절반을 고르고 있다.

### 9-1. 플랫폼 현실 — 자동 캡처는 불가능하다

| | **Android** | **iOS** |
|---|---|---|
| **백그라운드 클립보드 읽기** | ⚠️ **API 29(Android 10)부터 차단** — 포커스가 있거나 기본 IME일 때만 | ✕ **불가** — 포그라운드에서만 |
| 붙여넣기 읽기 | 위와 동일 | iOS 16+ **붙여넣기 권한 팝업**이 뜬다 |
| **클립보드 쓰기** | ✅ 포그라운드에서 가능 | ✅ 포그라운드에서 가능 |
| **상시 연결 유지** | △ 포그라운드 서비스로 가능(배터리·알림 상주) | ✕ 앱이 정지된다 → **푸시(APNs)가 필요** |

> 👉 **결론**: 모바일은 **"클립보드 매니저"가 아니라 "받은 항목 목록 + 탭하면 복사"** 가 된다.
> 데스크톱처럼 **자동으로 클립보드에 얹히는 동작은 iOS에서 원리적으로 불가능**하고, Android도 제약이 크다.

### 9-2. 실현 가능한 형태

| 기능 | Android | iOS | 비고 |
|---|:--:|:--:|---|
| 받은 항목 **목록 보기** | ✅ | ✅ | 앱을 열면 보인다 |
| 탭 → **로컬 클립보드에 복사** | ✅ | ✅ | ★ 이게 "붙여넣을 수 있는 상태"의 모바일판 |
| 새 항목 **알림** | ✅ | ✅(푸시 필요) | 알림 탭 → 앱 → 복사 |
| 공유 시트로 **보내기**(수동) | ✅ | ✅ | ★ 사용자가 명시적으로 보내는 건 가능 |
| **자동 캡처**(복사 감지) | ⚠️ 제한적 | ✕ | [§9-1](#9-1-플랫폼-현실--자동-캡처는-불가능하다) |
| 자동 클립보드 덮어쓰기 | ✕ | ✕ | 포그라운드 아니면 불가 |

### 9-3. 아키텍처에 미치는 영향

| 재사용 | 재사용 **불가** |
|---|---|
| ✅ `nclip-core`(도메인·항목 모델) · 암호화·키 계층 · **`nbeep-relay` 와이어** · `DeviceList` 검증([07 §2-2](07-device-rendezvous.md#2-2-소속--devicelist-검증이-본체)) | ✕ **UI 전체** — 자체 CPU 래스터라이저·winit은 모바일로 안 간다. **별도 얇은 클라이언트**가 필요(네이티브 또는 그에 준하는 것) |

> ⚠️ **이것이 최하순위인 진짜 이유**는 기능이 작아서가 아니라 **UI 계층을 한 벌 더 만들어야 하기 때문**이다.
> 공유되는 것은 **프로토콜과 도메인**이지 화면이 아니다.
> 추가로 iOS는 **APNs 푸시 서버 + Apple 개발자 계정**이 필요해 [05 §3](05-multi-device-sharing.md#3-별도-릴레이-서버를-만들어야-하는가--아니다)의 *"서버 코드 변경 0"* 이 **모바일에서는 깨진다**(푸시 중계가 새 서버 책임).
