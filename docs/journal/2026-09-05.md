## 11차(Linux VM) — ★ 아이콘이 개발 빌드를 띄우던 것 근절 — 패키지가 있으면 사용자 런처·자동 실행을 건드리지 않는다 (사용자 제보 09-05)

**제보**: "앱 표시에 있는 아이콘 클릭하면 debug 실행파일을 실행하고 있어." — 10차에서 원인을 밝혀 두었지만(앱이 시작마다 사용자 런처를 자기 경로로 덮어씀) 그때는 상태만 복구했고 **동작 자체는 그대로**였다. 실제로 되풀이돼 근절한다.

| 축 | 내용 |
|---|---|
| 근인 | `install_launcher`가 시작마다 `~/.local/share/applications/nexa-clip.desktop`을 **현재 실행 파일**로 쓴다. XDG 우선순위상 사용자 폴더가 `/usr/share`를 **가린다** → 개발 빌드를 한 번만 돌려도 아이콘·자동 실행이 개발 빌드로 넘어간다(그 인스턴스가 포털에 붙어 **전역 단축키 오염**까지 이어졌다 — 10차) |
| 규칙 | ★ **패키지가 설치돼 있으면 그 자리를 건드리지 않는다.** `packaged_install()` = 시스템 데이터 폴더(`XDG_DATA_DIRS`, 기본 `/usr/local/share:/usr/share`)에 우리 런처가 있고 같은 프리픽스의 `bin/nexa-clip`이 실재하면 패키지 설치본 |
| 수정(1차 — ❌ 불충분) | `install_launcher`가 패키지가 있으면 **사용자 사본을 지우고 손 뗐다**. 개발 빌드를 돌려도 파일이 안 생기는 것까지는 확인했으나 **사용자가 아이콘을 눌렀을 때 여전히 개발 빌드가 떴다** |
| ★ 왜 부족했나(사용자 ps가 잡아냄) | GNOME 셸은 앱 목록을 **캐시**한다 — 파일을 지운 뒤에도 **삭제된 그 경로를 든 채** 실행했다(실측: `GIO_LAUNCHED_DESKTOP_FILE=~/.local/share/applications/nexa-clip.desktop`인데 그 파일은 **존재하지 않음** · ppid = gnome-shell · exe = `target/debug/nexa-clip`). **지우기로는 캐시를 이길 수 없다** |
| 수정(2차 — 채택) | 패키지가 있으면 사용자 사본을 **지우지 말고 설치본을 가리키게 유지**한다. 캐시가 그 경로를 들고 있어도 파일 내용이 `/usr/bin/nexa-clip`이라 **설치본이 뜬다** · 내용이 바뀌면 셸 감시자도 깨어난다. 자동 실행 `register`는 그대로 패키지 실행 파일을 가리킨다 · 패키지가 없으면 종전 동작 |
| 실증 | 반영 후 **개발 빌드를 일부러 실행** → 사용자 런처·자동 실행 모두 `/usr/bin/nexa-clip` **유지**(종전엔 한 번에 넘어갔다) · 데스크톱/아이콘 캐시 재생성(`update-desktop-database` 사용자·시스템 · `gtk-update-icon-cache`) · ★ **사용자 재확인 완료(리부팅 후)** — 아이콘·자동 실행 모두 설치본 |
| ★ 마지막 한 조각 = **셸 재시작** | 파일을 옳게 고치고 `update-desktop-database`까지 돌려도 **이미 떠 있는 gnome-shell의 인메모리 캐시는 갱신되지 않았다**. 사용자가 리부팅하자 비로소 정상 동작. 실측(리부팅 후): 사용자 런처·자동 실행 `Exec="/usr/bin/nexa-clip"` · 실행 중 프로세스 `/usr/bin/nexa-clip`(**ppid = gnome-shell** = 아이콘/자동 실행 경로) · 단축키 저장소 `nexa-clip`에 `a1=<Shift><Alt>c`·`a3=<Shift><Alt>x`(`code` 오염 없음). **교훈: 런처 경로를 고친 뒤에는 셸 재시작(또는 재로그인)까지가 절차다** |
| ⚠️ 내 실수 | `gtk-launch`가 설치본을 띄운 것만 보고 **"해결됐다"고 단정**했다 — 아이콘을 누르는 주체는 gnome-shell이고 그 캐시는 다른 결과를 냈다. 사용자의 `ps -ef` 출력이 사실을 잡아냈다. **판정 기준은 실제 클릭 결과**여야 한다 |

**실측**: 3타깃 clippy ✓ · 테스트 전체 ✓ · 최종 = 아이콘·자동 실행 모두 설치본 · 단축키 등록 정상.

## 10차(Linux VM) — ★ 전역 단축키 불능 = GNOME 저장소에 **VS Code 이름(`code`)으로 등록된 우리 단축키** (사용자 제보 09-05)

**제보**: 앱 아이콘으로 실행했는데 단축키가 안 먹는다. + "deb에 아이콘 등록 기능이 있는지" + "자동 실행이 설치본인지".

| 축 | 내용 |
|---|---|
| **근인** | GNOME 전역 단축키는 **앱 이름(app id)** 으로 관리된다(`/org/gnome/settings-daemon/global-shortcuts/<앱>`). 내가 **VS Code 통합 터미널에서** 앱을 띄우는 바람에 cgroup이 `app-code-….scope` → 포털이 우리를 **`code`로 오인**해 그 이름으로 `<Shift><Alt>c`·`<Shift><Alt>x`를 잡았다(설명 문자열은 우리 것). 그 뒤 **정상 경로(앱 아이콘 = `app-gnome-nexa\x2dclip-…`)** 로 뜬 인스턴스는 같은 조합을 다시 못 잡아 **"등록 일부 실패"**, 키를 눌러도 **죽은 `code` 세션**으로 가 아무 일도 안 일어났다 |
| **진단이 막혀 있던 이유** | `hotkey_linux::spawn`이 `Err(_)`로 **사유를 버려** 셸이 "포털이 없거나 거부됨" 같은 **추측 목록**만 찍었다 → 오류를 그대로 남기게 고쳤고(`전역 단축키: 포털 등록 실패 — {e}`), 그 즉시 진짜 사유가 나왔다: **`org.freedesktop.portal.Error.NotAllowed: An app id is required`** |
| **스코프 이름 규칙(실측)** | `systemd-run --user --scope --unit=…`으로 띄울 때 앱 이름의 하이픈은 **`\x2d`로 이스케이프**해야 한다. `app-nexa\x2dclip-<n>.scope` ✅ · `app-gnome-nexa\x2dclip-<n>.scope` ✅ · **`app-nexa-clip-<n>.scope` ❌**(앱 이름을 못 읽어 `An app id is required`). GNOME 자신도 이스케이프 형식으로 띄운다 |
| **수정** | ① 잘못 등록된 `code` 항목 제거(저장소 = `['nexa-clip']`) ② `dev-install-linux.sh`가 **앱 이름 스코프**에서 띄우도록(`gio launch`는 **호출한 셸의 앱 스코프를 물려받아** 같은 오염을 만든다) ③ 포털 오류 사유를 로그에 남김 |
| **아이콘·자동 실행 검증** | `.deb`는 아이콘·런처를 **정상 등록**한다(`dpkg -L` — `/usr/share/applications/nexa-clip.desktop` · `/usr/share/icons/hicolor/256x256/apps/nexa-clip.png` · desktop-file-utils·hicolor 트리거 실행됨). 다만 앱이 **시작마다 `~/.local/share/applications/nexa-clip.desktop`을 자기 경로로 다시 써서**, 사용자 폴더가 시스템 폴더보다 우선하므로 **마지막에 실행된 빌드가 아이콘을 가져간다** — 그래서 아이콘이 개발 빌드를 띄우고 있었다. 자동 실행도 같은 이유로 개발 빌드를 가리켰다. 설치본을 다시 띄워 **둘 다 `/usr/bin/nexa-clip`으로 복구** |
| **잔여(T-41에 추가)** | 개발 빌드가 패키지 설치본의 아이콘·자동 실행을 **가로채는 동작** 자체 — "시스템 런처가 있으면 사용자 런처를 쓰지 않는다" 규칙이 필요 |

**실측**: fmt·clippy ✓ · nclip-plat 39 테스트 ✓ · 스코프 3형식 비교 실측 · 최종 상태 = `/usr/bin/nexa-clip` · 저장소 `['nexa-clip']` · `nclip-hotkey` 스레드 · 세션 `nclip_session`. **사용자 실기 ✓(09-05 리부팅 후)** — Shift+Alt+C 팝업 동작 · 저장소에 `code` 오염 항목 없음.

## 9차 — ★ beep 전달 내용을 **별도 문서**로: [32 전달문](../32-beep-handover.md) (사용자 요청 09-05)

|---|---|
| **A. 공용 `nexa-conf`**(이번에 새로 확인) | A-1 설정 파일이 umask 권한 → **0600 권함**(beep `lib.rs:106` `write_atomic`의 `File::create` · 실측 `settings.cfg`·`profile.sec`·`server.pin`·`trust.seg`·`keys.seg` **664** · `identity.key`만 600) · A-2 미지 키 무조건 재방출 → **같은 키 두 줄**(beep `lib.rs:71` `serialize` · clip은 `ui.set_*` 5키 등재 때 실제로 겪음). 둘 다 **clip이 적용한 패치와 회귀 테스트를 그대로 실었다** |

| **C. 서버 변경 대기** | C-1 공유 URID · C-2 오프라인 큐 · C-3 앱/버전 태그 — 전부 clip이 우회 중이라 **회신 불필요**(정보 공유) |

## 6차(Linux VM) — ★ 설치본 자리에서 실기: `dev-install-linux.sh`(win·mac 스크립트의 Linux 판) (사용자 요청 09-05)

**요청**: 배포판을 설치해 **실제 설치 위치 기준**으로 테스트하고, 이후 소스를 고치면 **릴리스 빌드 → 설치 위치에 복사 → 재설치 없이** 바로 실기. mac/win은 이미 스크립트로 같은 동작.

| 축 | 내용 |
|---|---|
| 기준선 | 새로 만들지 않고 **배포된 v0.1.1 자산**(`nexa-clip-0.1.1-linux-x64.deb`)을 쓴다 — CI가 zig 링커로 glibc 2.17 링크 + 심볼·크기 게이트를 통과시킨 **사용자가 받는 그 산출물**. 로컬 `Cargo.toml`도 0.1.1이라 버전 어긋남 없음. 설치가 만드는 것은 위치·런처·아이콘·패키지 등록이고 바이너리는 곧 덮어쓰므로 최초 설치본이 최신일 필요가 없다 |

## 2차(Linux VM) — ★ 호스트 mac과 LAN 직결 불능 = 게스트 러너 미기동 → 릴레이 None 자동 재기동 (사용자 실기)

**환경**: 이 Linux 개발 PC = **VMware Fusion 게스트**(ens33 192.168.80.131/24 · NAT 게이트웨이 .2) · 호스트 mac = bridge101 192.168.80.1
(기본 경로는 en0 192.168.45.84). 사용자가 게스트 설정 창에서 릴레이 `none` + 핸들/암호를 채웠는데 mac과 만나지 못함.

| 축 | 내용 |
|---|---|
| 진단 | 로그에 "LAN 직결: 비콘 …" 기동 줄 없음 · `ss`에 47301/udp 없음 · `identity.key` 미생성 → **러너가 한 번도 뜨지 않았다** |
| 근인 | 입력 **순서**: Enable → 릴레이 none(재기동 계기 ✓ · 그러나 핸들/암호 빔 → `Unconfigured`) → 기기 이름 → 핸들 → 암호. 핸들·암호 행 변경은 재기동 계기가 아니었다(`settings_win` — `sync.relay`·`sync.enabled`만 봄). 남은 계기 = Test·재시작 |
| 검증 | `dev-restart.sh`로 재시작 → 부팅 경로가 채워진 설정을 읽어 러너 기동 → 14초 안에 **mac이 접속**(`← 192.168.80.1:55362 수락` · `기기 연결(LAN) — kiros33@mac · 새 기기`) · devices.txt에 mac 등재(미승인) |
| 수정 | ★ **릴레이 None 자동 재기동** — `sync.handle`·`sync.passphrase`(생성 버튼 포함) 변경 시 `lan_auto_respawn_ready`(none · on · 둘 다 있음)면 **800ms 디바운스** 뒤 `sync_respawn`(DR-41 마지막만) · `about_to_wait`가 만료에 깨어나도록 WaitUntil 병합 · 서버 릴레이는 종전 계약(해제 → Test) 유지 · 단위 테스트 1 |
| 부수 발견 | ★ **비콘은 한 방향만** — 송신 대상 = 255.255.255.255 + **기본 경로** /24. 호스트 mac의 기본 경로는 en0라 192.168.80.255로는 안 나간다(게스트에서 47301 12초 청취 = 0건). 이번에 붙은 건 mac 키 hex가 작아 **mac이 다이얼하는 차례**였기 때문 — 키가 반대면 영영 안 붙는다 → **T-26 "인터페이스 열거"** 그대로(전 IPv4 인터페이스 지향 브로드캐스트 필요) |

**설정 저장 로직 문의(사용자 — 글자마다 저장?)**: 이미 구현 — `nexa-conf::SaveScheduler`(`conf.rs` QUIET 1s · MAX_DELAY 10s). 변경은 `mark`(플래그만) ·
저장은 설정 창 `about_to_wait` 틱(dirty 동안 250ms)에서 **조용해진 지 1s OR 첫 미저장 후 10s**에 1회. Windows 로그의 "설정 변경" 줄은 글자마다 찍히지만
"설정 저장"은 입력 묶음(7자)당 1회였다. 연속 "설정 저장" 2줄 = 틱 저장 + 창 숨김 flush(기하 저장). 변경 없음.

**실측**: clippy 0(신규) · `lan_respawn_tests` 1/1 · 20 스위트. ⏳ 사용자 실기: 게스트 설정에서 암호를 지웠다 다시 채우면 ~1초 뒤 로그에
"LAN 직결: 비콘 …"이 다시 서고 mac이 재접속하는지 · 양쪽 기기 행 6자리 대조·승인 → 복사 전파(21 §6 S3~).

## 2차(macOS) — ★ 기기 이름 변경 재소개 — 저장 박자에 연결된 세션 전부로 · PeerId 기준 자동 갱신 (사용자 요청)

**요청**: 이름을 여러 번 고쳐 저장(tick)되는 시점에, 지금 연결된/앞으로 연결할 기기들에 새 이름을 다시 소개 · 이미 등록된
기기는 PeerId 기준 자동 갱신 · **LAN·릴레이 모두** · **미승인 기기도 갱신**(최신 이름을 보고 승인할 수 있게).

| 축 | 내용 |
|---|---|
| 종전 | `set_device_name`만 즉시 — 인사(Hello)는 세션 시작 때 한 번이라 살아 있는 세션은 재접속 전까지 옛 이름 |
| 송신 | 세션 채널 메시지를 `PeerCmd { Item, Hello }`로 확장 · `announce_name()` = `PEER_TX` 전부(승인 무관 · 릴레이/LAN 공통)에 Hello 명령 · 세션 루프가 현재 `display_name`으로 `NCH1` 재전송(로그 "이름 재소개") |
| 수신 | 세션 중 Hello = `upsert_online`(PeerId 기준 이름·OS 갱신 · 승인 무관) + `devices.txt` 저장 + `SyncTick`(설정 Report 행 갱신) · 로그 "기기 이름 갱신 — old → new"(첫 인사와 구분) |
| 시점 | 설정 창 `sync.device_name` 변경 → **1s 디바운스**(nexa-conf SaveScheduler quiet 1s와 같은 박자 = "저장 시점") → `fire`에서 재소개 · `WaitUntil` 병합 · 연속 입력은 마지막만(DR-41) |
| 와이어 | `NCH1` 재사용 — Noise 안 논리 메시지 · 서버·beep 변경 0(docs/22 대상 아님) |

**실측**: clippy 0 · 테스트 통과(sync 19 · nexa-clip 59) · 설치본 교체. ⏳ 실기: 두 PC 연결 중 한쪽 이름 변경 → 1초 뒤 상대 기기 목록에 새 이름(미승인 상태 포함).

## 1차(macOS) — ★ 수신 이미지가 "[이미지]"로만 — 팔레트 PNG 디코드 거부 (사용자 실기)

**제보**: Windows에서 전파된 이미지(⇄ kiros33@win · 1222×106)가 목록·미리보기에 섬네일 없이 라벨만. 로컬 이미지는 정상.

| 축 | 내용 |
|---|---|
| 진단 | `nclip-store` 예제 **`dump_item`** 신설(라벨 부분 일치 → 표현·blob 바이트 파일로) → 저장된 표현 = `public.png` 4598B, `file` 판정 **8-bit colormap**(팔레트) |
| 근인 | `nclip-imgdec::decode_png` — `ColorType::Indexed => return None`(팔레트 거부). Windows는 CF_DIB가 함께 있어 가려졌고, 원격 수신(mac `public.png` 한 표현)에서 드러남 |
| 수정 | `png::Transformations::EXPAND \| STRIP_16` — 팔레트→RGB(A)(tRNS→알파) · 저비트 그레이 확장 · 16→8비트. 회귀 테스트(팔레트 PNG 인코드→디코드 RGBA 단언) |
| 검증 도구 | `nclip-plat` 예제 **`decode_probe`**(3-OS · 파일 → 격리 워커 디코드). 실제 바이트 384×33 ✓ · 설치된 워커로도 ✓ |
| 함정 | `cargo build --example …`을 `-p nclip-imgdec`와 함께 주면 **bin 타깃이 안 만들어진다** — 낡은 워커를 복사해 첫 검증이 헛돌았다(산출물 시각으로 발견) |

**실측**: clippy 0 · 20 스위트(+1) · 설치본 교체.

**회신 2(사용자: 미리보기 ✓ · 섬네일 ✗ · 수신 표시 사라짐)**:
- 섬네일 ✗ = `pump_thumbs`가 RAM 섬네일/blob 참조 없는 항목을 영구 `fail` — 캡처 때 생성 실패분(옛 워커·팔레트)은 자가 복구 불가
  → ★ **자가 치유**: 이미지 계열이면 본문 표현에서 `decode_image`로 만들어 표시 + `encode_raw_isolated` → `ThumbEncoded`(마이그레이션 경로)로 PNG blob 영속.
- 수신 표시 사라짐 = **결함 아님** — 제 디코드 검증(`osascript set the clipboard … PNGf`)이 같은 PNG를 mac 클립보드에 올려
  **로컬 항목(#69 · 출처 Code)** 으로 캡처됐고, 중복 제외(로컬 우선)가 수신본(#66 · ⇄)과 한 행으로 합쳐 대표를 로컬로 바꿈(덤프로 확인).
  공유 대상·승인과 무관. 중복 제외를 끄면 두 행(수신본 = 녹색 점)이 보인다.
