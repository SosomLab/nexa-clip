### ② ★ 원인 특정 — 검수 환경 탓이 아니라 **우리 바이너리 결함**이다

이 PC의 릴리스 산출물 임포트 테이블을 직접 읽었다(바이트 스캔 · 덤프 도구 불요):

```
nexa-clip.exe    … VCRUNTIME140.dll · api-ms-win-crt-{heap,locale,math,runtime,stdio}-l1-1-0.dll
nclip-imgdec.exe … VCRUNTIME140.dll · api-ms-win-crt-*
```

**`VCRUNTIME140.dll`은 Windows 구성요소가 아니다** — VC++ 재배포 패키지로만 깔린다. Rust `*-pc-windows-msvc`의 기본값이 **CRT 동적 링크**라 우리는 그동안 "VC++ 재배포 패키지가 이미 깔린 PC에서만 도는 앱"을 배포하고 있었다. 개발기·실기 PC는 전부 그 조건을 만족해서(빌드 도구가 깔아준다) **한 번도 안 드러났다**. 검수기의 깨끗한 이미지가 처음으로 맨살을 밟은 것이다.

★ 이건 검수 통과 문제가 아니라 **사용자 결함**이다 — 깨끗한 Windows에서 Nexa Clip은 **실행 즉시 죽는다**. `단일 바이너리`(DR-1 전제)와도 어긋난다.

### ③ 수정 — 정적 CRT + 게이트 + **다시 조용히 깨질 자리 봉인**

- `.cargo/config.toml` — `x86_64`·`aarch64-pc-windows-msvc`에 `-C target-feature=+crt-static`.
- ★ **`release.yml`의 env `RUSTFLAGS: -D warnings` 제거**. env `RUSTFLAGS`는 `.cargo/config.toml`의 target별 `rustflags`를 **통째로 덮어쓴다** — 그대로 뒀으면 로컬에선 정적 CRT가 되고 **릴리스 산출물만 조용히 동적 CRT로 나가** 같은 일이 반복됐다. 경고 게이트는 `ci.yml`(clippy `-D warnings`)·`check-3os.sh`가 이미 맡고 있어 잃는 것이 없다. config·워크플로 양쪽에 경고 주석을 박았다.
- ★ **Windows DLL 게이트 신설**(`release.yml` — Linux glibc 심볼 게이트의 짝) — 산출물에 `vcruntime*`/`msvcp*`/`msvcr*` 임포트가 보이면 **배포를 멈춘다**. 원인이 "플래그가 조용히 빠지는 것" 하나뿐이라 산출물에서 직접 본다.

**검증**(x64 로컬 실측):

| | 전 | 후 |
|---|---|---|
| `nexa-clip.exe` 임포트 | `VCRUNTIME140.dll` + `api-ms-win-crt-*` | ★ **없음** — `KERNEL32`·`USER32`·`gdi32`·`ole32`·`shell32`·`uxtheme`·`dwmapi`·`imm32`·`shcore`·`bcrypt`·`advapi32`·`ws2_32`·`ntdll`·`dbghelp`(전부 OS 기본) |
| `nclip-imgdec.exe` 임포트 | 동일 | ★ **없음** |
| 크기 | 1,709,056 / 408,576 B | 1,815,552(+104KB) / 506,368(+95KB) — 10MB 게이트 여유 |

**게이트** — `cargo test --workspace` **539 passed · 0 failed** · `check-3os.sh` 3타깃 clippy + fmt ✓. arm64 Windows는 **컴파일 통과**(링크 인자에 `/defaultlib:libcmt` = 정적 CRT 확인)했으나 이 PC에 MSVC arm64 크로스 도구가 없어 **링크는 CI 러너가 검증**한다(이 변경과 무관한 기존 제약 · 새 DLL 게이트가 두 타깃 모두 검사).

⚠️ **Git Bash 함정** — `cargo build --target aarch64…`를 Bash 도구로 돌리면 coreutils `link`가 MSVC `link.exe`를 가려 `link: extra operand`로 죽는다. Windows 타깃 링크는 PowerShell에서.
