## 5차(Linux VM) — ★ **파일 항목 붙여넣기 3결함 수정**(평문 무시 · 경로 폴백 Windows 전용 · **X11 평문 별칭 누락**) (사용자 실기·요청 09-13)

**신고**: "팝업에서 파일을 선택하고 `Shift+Enter`를 눌러도 경로 붙여넣기가 안 된다" → 확인 중 "**`Alt+Enter`로도 안 된다**".

세 결함이 겹쳐 있었다. 앞의 둘은 코드를 읽어 찾았고, **셋째는 실측 TARGETS를 보고서야 나왔다**.

| # | 자리 | 무엇이 잘못됐나 |
|:--:|---|---|
| **ⓐ** | [`resolve_remote_files`](../../crates/nexa-clip/src/tray_cmd.rs) | `PathOnly`만 텍스트로 갈라내고 **`Plain`은 `Original`과 같은 가지**로 흘렀다 → 파일 표현이 만들어지고, **Linux는 표현 하나만 게시**([`pick_rep`](../../crates/nclip-plat/src/clipboard.rs))라 파일 표현이 이겨 **텍스트가 통째로 사라진다**. 로그가 증거 — 평문도 원본과 똑같이 `표현 3개 게시`. 덤으로 평문인데 **원격 내용을 끌어왔다**(docs/26 §4-5 취지 위반) |
| **ⓑ** | [`reps_for_mode`](../../crates/nexa-clip/src/tray_cmd.rs) | 경로 합성 폴백이 **`CF_HDROP`에서만** 경로를 뽑아 **Windows 전용**이었다 → Linux(`gnome-copied-files`)·**mac**(`NSFilenamesPboardType`)은 빈 표현 → 아무 일도 안 일어난다(로그 `이 항목에는 그 방식의 표현이 없습니다` · 설치본은 콘솔이 없어 안 보인다) |
| ★ **ⓒ** | [`selection_x11::publish`](../../crates/nclip-plat/src/selection_x11.rs) | 별칭(`UTF8_STRING`·`STRING`·`TEXT`)을 **`"text/plain"` 정확 일치**일 때만 달았다. 그런데 `plain_text_reps`가 합성하는 텍스트(경로만·평문·편집)는 **`text/plain;charset=utf-8`** 이다 → **별칭 없이 나간다**. 실측: `xclip -t TARGETS -o` = `TARGETS · TIMESTAMP · MULTIPLE · text/plain;charset=utf-8` **넷뿐** → GTK·Qt·터미널은 붙여넣지 못한다 |

★ **ⓒ가 "`Alt+Enter`도 안 된다"의 진범**이다. 게시는 성공하고(`재적재: 표현 1개 게시`) 주입도 성공하는데(`붙여넣기: 포커스 복원 + 키 주입 ok`) **받는 앱이 가져갈 타깃이 없어서** 아무 일도 안 일어났다 — 로그만 보면 전부 성공이라 안 보이던 자리다. 그리고 이것은 **09-05 Linux 감사 [T-41 ③]이 이미 지목한 결함**인데, 그때는 원인을 도구 파이프(`xclip`)로 짚었다. 실제 범인은 **네이티브 X11 게시**였다. **감시가 잡은 텍스트는 `text/plain`이라 별칭이 붙어** 평범한 텍스트 붙여넣기는 멀쩡했고, 그래서 **합성 텍스트에서만** 증상이 났다.

**수정**

- ⓐ `PasteAs::is_text_only()`(평문·경로만) 신설 — 파일 항목에서 둘은 같은 뜻(`filter_reps` 주석이 이미 *"파일 항목의 평문 = 경로 텍스트"* 라고 적어 둔 규칙을 실제로 지킨다) · 둘 다 **받아오지 않는다**.
- ⓑ 폴백을 `capture::paths_of`로 — CF_HDROP·NSFilenames·uri-list·gnome/KDE를 이미 전부 안다. 파일이 아니면 종전대로 SVG 글자 추출로 내려간다.
- ⓒ 게시의 평문 판정을 순수 함수 `is_plain_text_format`으로 빼고 **두 철자 다** 받는다.
- 곁들여 `reps_for_mode`를 **순수 함수**(`&[RawRep]`)로 바꿨다 — `HistoryItem` 조립 없이 3-OS 표현을 그대로 넣어 볼 수 있다(결함 ⓑ가 테스트 없이 산 이유가 이것이었다).

**게이트**: **538 테스트**(신규 5 + 실 X11 왕복 1(ignored) — 3-OS 파일 표현 각각에서 경로만·평문이 경로 텍스트를 내는가 · 기존 평문 표현 우선 · 비파일 항목은 정직하게 빈 표현 · `is_text_only` · 두 철자 별칭) · `check-3os` 3타깃 + fmt ✓.

**★ 실 X 서버 증명(추정 금지)** — `x11_synth_text_advertises_aliases`(`#[ignore]` · `DISPLAY=:0`)를 붙여 **합성 텍스트를 실제로 게시하고 TARGETS를 읽었다**.

| 코드 | 광고된 TARGETS | 테스트 |
|---|---|---|
| 수정 전 판정으로 되돌림 | `TARGETS · TIMESTAMP · MULTIPLE · text/plain;charset=utf-8` ← **사용자가 겪던 그 목록** | ❌ FAILED |
| 수정 후 | `… · STRING · text/plain · UTF8_STRING · COMPOUND_TEXT` | ✅ ok |

즉 이 결함은 이제 **실기 없이 회귀로 잡힌다**. 설치본 교체 `pid 44323`(해시 = release 동일) · mac 재연결 확인.

**교훈** — ① *"게시 성공 + 주입 성공"* 로그가 **붙여넣기 성공을 뜻하지 않는다**. X11은 **광고한 타깃**이 계약이라, 그 목록을 보지 않으면 성공처럼 보이는 실패가 남는다. ② 같은 뜻의 MIME 두 철자(`text/plain` · `text/plain;charset=utf-8`)를 **판정하는 곳마다 따로** 적어 둔 것이 근인이다 — 읽기 쪽은 정규화하고 쓰기 쪽은 정확 일치를 썼다. ③ 09-05 감사가 증상을 맞게 적고 **원인을 틀리게 짚었다**(도구 파이프 ← 네이티브 게시) — 감사 항목은 "어디를 고치면 되는가"까지 실측해야 값이 선다.

**② `x-special/nautilus-clipboard`는 우리 표기가 아니다 — Nautilus의 레거시 `text/plain` 표식이다**

목록 4번 행의 세 줄(`x-special/nautilus-clipboard` / `copy` / `file:///var/run/vmblock-fuse/blockdir/vMOJ4n/XGDY9331.JPG`)은 **항목의 내용 그 자체**다. ★ **여기서 결함이 하나 드러난다(T-55)** — clip은 `x-special/nautilus-clipboard`를 **형식 이름으로만** 알고([`capture.rs`](../../crates/nclip-core/src/capture.rs) `is_file_format`·`paths_of`), **내용에 든 표식은 못 읽는다**. 재현 실험(같은 형태를 `text/plain` 하나로 올림) 결과:

```

동기화: 항목 전파 → 기기 1대        ← 생 문자열이 그대로 mac으로 간다
```

따라서 ⓐ 목록에 생 문자열 항목이 남고 ⓑ **상대 기기에 그대로 전파되며** ⓒ 붙여넣으면 파일이 아니라 그 문자열이 붙는다. 처방은 평문 첫 줄이 표식이면 나머지를 파일 관리자 표현과 **같은 규칙**으로 읽어 파일 항목으로 승격하는 것 — **T-53(잘라내기 동사)과 같은 파서**를 건드리므로 함께 결정한다.

## 2차(mac) — ★ 다른 PC 파일이 **바로 붙여넣기되지 않던 문제**(사용자 실기) — 최신 약속 즉시 받기 + 완료 시 클립보드 반영 (사용자 요청 09-13)

**증상**(사용자): "다른 PC에서 복사된 파일이 붙여넣기 시 바로 반영되지 않고, 다시 선택한 다음 붙여넣기를 하면 됨. 최신 클립보드로 복사되지 않는 것 같다".

**원인 — 버그가 아니라 09-12 결정 둘의 합**:

| # | 어디 | 무엇 |
|---|---|---|
| ① | `apply_remote` | 약속(매니페스트)은 **게시하지 않고 return**(2차 "붙여넣을 때 받는다") — 텍스트·PNG는 같은 자리에서 즉시 `set_reps` |
| ② | `on_xfer_done` | 사전 캐시 완료 시 **게시 안 함**(4차 — 핑퐁 방아쇠였음) → 클립보드엔 여전히 **그 전 내용** |
| — | 결과 | Ctrl+V = 옛 내용 · 목록에서 고르면 `resolve_remote_files` 캐시 적중으로 그제야 게시 → 두 번째에 됨 |

DR-28("수신측은 바로 시스템 클립보드에 반영")이 파일에서만 빠져 있었다. 5차의 구조 가드(`from_reps`가 캐시 경로 페이로드를 안 만듦)가 들어간 뒤라 **캐시에서 게시해도 연쇄가 불가능** → 4차가 껐던 게시를 조건부로 되살렸다.

**수정**:

| # | 어디 | 무엇 |
|---|---|---|
| ① | `xfer::Manager::boost(item_id)` | 그 항목의 진행 중 전송을 **Fg**로 — 저속 상한(`file_bg_kbps`) 없이 · 다른 Bg는 양보. 상한 판정(`file_auto_mb` · 0 = 끔)은 `fetch(Bg)`가 이미 했으므로 자동 캐시 설정 의미는 그대로 |
| ② | `on_captured` | 받은 약속을 Bg로 줄 세운 직후 `boost` — 로그 "즉시 받기(Fg n · 저속 상한 없음)" |
| ③ | `on_xfer_done` | 사전 캐시 완료 + 붙여넣기 대기 없음 → **그 항목이 아직 이력 맨 앞이면 게시**(`publish_cached` — 파일 표현 + 경로 텍스트 · `expect_echo`) · 맨 앞이 아니면 종전대로 배지만(사용자의 더 새 클립보드를 덮지 않는다). 게시 블록은 `publish_cached`로 뽑아 붙여넣기 대기 경로와 공용 |

**안전**: 게시 → 감시 되읽음 → `on_captured` 캐시 에코 승격(4차) · 전파는 `from_reps` 구조 가드(5차)로 불가. 알림은 텍스트 수신과 같이 없음(로그만). 상한 초과·자동 캐시 0인 항목은 내용이 없어 종전(고른 뒤 받기) 그대로.

**검증**: 테스트 `boost_lifts_background_to_foreground`(bg 1 B/s에서도 boost 뒤 완료 · 이미 Fg면 0 · 자동 캐시 끔이면 0) · 537 테스트 ✓ · 3-OS ✓. ⏳ **실기**: A 복사 → B에서 곧바로 Ctrl+V = 파일(작은 파일은 즉시 · 큰 파일은 받는 시간 뒤) · B가 그 사이 다른 것을 복사했으면 덮지 않음 · 핑퐁 없음.
