## 9차 — beep UI 재사용 계획 (사용자 방침)

사용자 방침: *"기본적인 UI는 Beep의 골격과 설정화면 등 되도록 그대로 사용해서 빠르게 개발하려고 해."*

**추정하지 않고 실코드를 쟀다.** 결과가 기대보다 좋았다.

- ★ **`nbeep-ctl`은 의존이 `nbeep-gfx` 하나뿐이다.** Cargo.toml 주석이 그대로 설명한다 — *"앱 도메인(nbeep-core 등) 의존 금지 — 이 크레이트의 존재 이유다. 문자열(i18n)·크기 배율 같은 앱 정책은 전부 주입으로 받는다."* → **11,214 LOC 무수정 이식**.
- ★ **설정 화면이 `Entry` 레지스트리 단일 원천 구조**다. `settings.rs` 헤더: *"영속 설정 전부가 registry()에 등록되고, 렌더와 검색이 같은 원천을 읽는다 — '화면에 있는데 검색 안 되는 설정'이 구조적으로 불가능하다."* 도메인 의존은 **`Entry` 배열과 `HIDDEN_KEYS` 뿐** → **화면 코드 한 줄 안 고치고 목록만 교체**하면 3,510 LOC가 그대로 산다. 사용자 요구가 가장 잘 맞아떨어진 지점.
- ★ **`MenuBar`(pulldown.rs:56) · `Toolbar`(toolbar.rs:129) · `TreeGrid`+`GridColumn`+`FlatRow`(tree.rs:502·483·81)가 이미 있다.** 8차에서 확정한 메인창(메뉴바+툴바+검색바+목록)이 **기존 컨트롤로 조립된다**. → **정정: `nexa-dir2` `grid`/`columns` 이식이 불필요해졌다**(D-36).

**합계**: 무수정 12,338 + plat 선별 3,713 + 프레임워크 재사용 5,580 ≈ **21,600 LOC**. 버리는 것은 beep 도메인 UI ~10,000(chat_view 3,393 · peer_list 2,342 · profile 1,533 등)이고, `app.rs` 18,538은 **패턴만**(WinEntry 맵 · 부분 무효화 · take_changes 폴링 · IME 게이트) 가져온다.

**결합 방식(D-8 확장)을 세 안으로 비교**했다. path 의존(A)은 즉시 빠르지만 beep이 지금도 활발히 바뀌고 있어 clip이 깨진다. 별도 저장소 승격(C)은 정석이나 3-저장소 운영 비용이 지금은 크다. → ★ **B(복사) + 규율 U-1**을 권했다: **복사한 파일은 고치지 않고, 확장은 우리 크레이트에서만**. *"복사해 놓고 조금씩 고치기"* 가 가장 나쁜 결말이라 **파일 단위로 경계를 강제**한다 — beep이 `nbeep-ctl`에 도메인 의존을 금지한 것과 같은 종류의 규율이다. U-1을 못 지키는 상황이 두 번 이상 나오면 C로 승격 재검토.

**손봐야 할 결합 하나**: `nbeep-ui`가 `nbeep_core::{current_lang, tr, Lang, Msg}`에 의존한다 → `nclip-core`에 **같은 이름·같은 형태**로 두면 이식 코드의 `use` 경로만 바뀐다(D-35). `nbeep-ctl`은 문자열을 주입받으므로 이 문제가 없고, 그래서 무수정 이식이 가능하다.

**착수 순서를 다시 짰다** — UI를 먼저 세워 눈에 보이게 하고 어려운 `plat`을 그 위에 붙인다. ★ **3단계(설정 화면 이식)에서 이미 "설정이 열리는 앱"이 된다.** 사용자 방침("빠르게")에 가장 크게 기여하는 지점이라 앞으로 당겼다.

⚠️ **UI를 통째로 물려받으니 [02 K-1](02-roadmap.md#7-리스크--일정을-실제로-흔들-것) 판단이 더 선명해졌다** — 새로 쓸 것은 **클립보드 감시(3-OS)** 와 **전역 단축키 + 포커스 복원 + 키 주입** 둘이고, beep에는 **둘 다 없다**(clipboard.rs는 읽기/쓰기만 있고 watch가 없다).

## 8차 — 비전·로드맵 + Rich Text 포맷 + 화면 구성 확정 (사용자 요청)

**요청 1**: *"최신 클립보드 프로그램의 핵심 편의성과 기능을 정리하고, 기능별 개발 진행 목표를 제시해줘."*

기능 매트릭스([03](03-competitive-landscape.md))만으로는 **왜 어떤 제품은 매일 쓰이고 어떤 제품은 안 쓰이나**를 설명하지 못한다는 판단에서, **편의성을 별도 축으로 분리**해 [00 비전](00-vision.md)을 세웠다. **핵심 편의성 8**(3초 · 키보드 완결 · 잊게 하는 상주 · 눈으로 골라내기 · 알아서 안전 · 되돌아감 · 맥락 유지 · 기기 경계 없음)을 전부 **측정 가능한 기준**으로 적었다 — 팝업 ≤100ms, 검색 갱신 ≤16ms 같은 식. 각 성질에 **무너지면 나타나는 증상**을 붙여 반증 가능하게 했다.

2026년 흐름 11건(T-1~T-11)을 조사해 우리 입장을 정리했다. 중요한 발견 둘:
- ★ **PowerToys Advanced Paste가 로컬 OCR을 쓴다** — OCR이 **외부 전송 없이** 되므로 "로컬 전용" 원칙과 충돌하지 않는다. D-7(OCR)이 **채택 쪽으로 기운다**.
- ★ **업계가 Electron→Tauri로 한 칸 움직였다**(EcoPaste·PasteBar). 그런데 **Tauri도 OS WebView에 의존**한다 → 우리가 그 한 칸을 더 가는 것이 차별점 ①의 실체.

[02 로드맵](02-roadmap.md)은 시간 계획이 아니라 **성숙도 계획**으로 짰다 — 기능 영역 10개 × M1~M4 매트릭스 + 단계별 **측정 가능한 수용 기준**. 원칙 R-1(*각 단계가 그 자체로 완결된 제품*)과 R-3(*편의성 ①~⑦은 M1에서 전부*)이 핵심이다. 리스크 K-1(포커스 복원+키 주입)을 최우선 스파이크 대상으로 못 박았다.

**요청 2**: *"워드나 PPT 등의 Rich Text 기능도 필요, 일반 텍스트로 붙여넣기 기능도 필요."*

★ **이 요구를 HTML/RTF 보존으로만 구현하면 안 된다는 것**이 [12](12-clipboard-formats.md)의 결론이다. Office는 클립보드에 **여러 표현을 동시에** 올리고, PPT 도형은 `Art::GVML ClipFormat`, Excel 범위는 `XML Spreadsheet` 같은 **원본 형식**에 실려 있다. HTML/RTF만 보관하면 **PPT 도형이 그림으로 떨어지고 Excel 수식이 값으로 떨어진다**.

→ **FR-C-5·FR-C-6을 P1 → P0로 승격**하고, 저장 모델을 **"이름째로 전부 보관"**(F-1 — 해석하지 않는다)으로 잡았다. 붙여넣기는 4모드(원본 그대로 / 평문 / 서식만 제거 / 표현 선택)로 나누고 FR-P-9~12를 신설. 파생 문제 셋도 같이 처리했다 — **크로스 OS 정규화**(Win `CF_HTML`은 오프셋 헤더가 붙는다 · mac/Linux는 순수 HTML), **원본 형식은 같은 OS끼리만 전달**(상대에 그 앱이 없으면 무의미), **표현별 차등 수명**(Office 클립보드는 수 MB — 평문·HTML은 오래, 무거운 원본 형식은 짧게).

**요청 3**: 트레이 우클릭 메뉴 + 메인창 구성(메뉴바·툴바·검색바·3보기).

[04 §2-2·§2-4](04-feature-scope-and-screens.md)를 사용자 지정대로 다시 썼다. 이전 설계의 S2는 파일 탐색기식 그리드였는데, **메뉴바 + 툴바 + 검색바 + 목록**의 고전적 데스크톱 구성으로 교체했다.

- **진입점이 셋으로 정리됐다** — 전역 단축키→퀵 팝업(키보드 사용자·3초) / 트레이 우클릭→최근 8개(마우스 사용자) / 메인창(탐색·정리). 각각 다른 사용자를 위한 것이라 중복이 아니다.
- **보기 모드 3종**을 렌더 규격까지 적었다: 일반(가변 높이·서식 렌더) / 간략(고정 1행 + 작은 썸네일 · **기본값**) / 한 줄(평문 1줄·최대 밀도). V-1로 **일반 보기는 가변 행 높이라 높이 캐시가 필요**함을 명시했다.
- ⚠️ **V-4가 보안 요구다** — *"리치텍스트를 그대로 보여준다"* 를 순진하게 구현하면 HTML 렌더러가 공격면이 된다. 우리는 브라우저 엔진이 없으므로(DR-1) **굵기·색·표·목록만 그리는 제한 렌더러**를 쓴다(FR-U-16 신설).
- ⚠️ **메뉴바는 macOS에서 창 안에 그리지 않는다** — 시스템 메뉴바에 미러링. DR-2의 *"동작 관례는 각 OS 네이티브"* 가 적용되는 지점이고, 여기까지 통일하면 맥에서 못 쓰는 프로그램이 된다.
- **정규식 검색은 메인창에만** 둔다(FR-F-6 P2→P1). 퀵 팝업은 [00 §2 ①](00-vision.md)의 3초를 지켜야 하므로 단순 타입어헤드만 유지.

**결정 갱신**: DR-11(Rich Text + 평문) · DR-12(화면 구성) 확정 추가. 기존 "확정 대기" 항목은 번호 충돌을 피해 이동(08-26 재정리로 **DP-1~4 계열**이 됐다). 열린 결정은 D-30~D-34가 늘어 **총 34건**.

## 7차 — 문서 골격 수립 + 초기 커밋 (사용자 요청)

`nexa-beep`/`nexa-dir2`의 4층 문서 체계를 이식했다. [16 문서·git 규약](16-doc-git-conventions.md)은 beep에서 그대로 차용하되 헤더만 이 저장소 기준으로 고쳤다(적용 실체 = README + 10-decision-record, `15`·`18`은 코드 착수 시 생성으로 번호 예약).

## 6차 — 신원과 페어링 ([09](09-identity-and-pairing.md))

사용자 제안: *"UserId는 직접 등록해 느슨하게 관리하고, 동일 UserId 중 연결 가능한 PeerId를 사용자가 직접 등록해 신뢰성을 올린다."* + 제약: *"길거나 못 외우는 값, 기존 PC를 봐야 하는 방식은 즉시 사용이 어렵다."*

**평가**: 뼈대가 옳다 — 신뢰의 출처를 이름이 아니라 **사람의 승인**에 두는 것이 이 문제의 정답 형태다. 다만 **구멍이 하나** 있다.

**구멍(R-a)**: 핸들 문자열에서 랑데부 ID를 파생하면 `RID = H("kiros33" ‖ epoch)` 를 **누구나 계산**할 수 있어, 흔한 아이디 사전으로 **온라인 여부를 대량 스캔**할 수 있다. beep 회전 RID가 지키던 성질이 무너진다. 파생 문제(R-b 연결 폭주 → **R-d 승인 피로**)가 더 위험하다고 판단했다 — *보안은 뚫려서가 아니라 닳아서 무너진다*.

**삼각 트레이드오프를 세워 보니** 사용자 제약 셋(열거 저항 · 기존 PC 불필요 · 짧고 외울 수 있음)을 **동시에** 만족하는 안이 하나 있었다:

> **핸들(공개·짧음) + 페어링 패스프레이즈(비밀·본인이 정함)** → `RID = PBKDF2-HMAC-SHA256(암호, "nclip-rid-v1"‖핸들‖epoch_day)[..16]`

- 비밀을 **기존 기기에서 가져오는 대신 사용자 머릿속에서 가져오기** 때문에 삼각형이 깨진다.
- 핸들이 salt에 들어가 **R-c(핸들 충돌)도 같이 사라진다**.
- `sha2`만으로 구현되어 **DR-8(외부 crate 0 지향) 유지**.

**타협하지 않은 것**: 랑데부가 성립해도 **사람의 승인**은 남긴다. 없애면 패스프레이즈를 아는 것만으로 클립보드 전체에 접근하게 되고, 클립보드는 비밀번호가 매일 지나가는 통로다. 대신 마찰을 낮췄다 — 승인은 *입력*이 아니라 **6자리 숫자 대조(보기)**, 기기당 1회, **페어링 창이 열린 동안만** 랑데부 개방(R-b·R-d 원천 차단).

**UserId 키의 존재 이유를 수치로 정리**: 쌍별 승인이면 5대에 10회 페어링, UserId 키 서명이면 **4회**. 새 기기는 **아무 기존 기기 하나와만** 붙으면 나머지가 자동 수용 — 사용자가 말한 "느슨한 관리"에 정확히 부합한다. 승인 권한은 **느슨(아무 기기나) + 전 기기 알림 + 주 기기 거부권**을 권했다(beep DR-28 *"신원이 바뀌면 시끄럽게"*).

## 5차 — 자동 전파 + 모바일 ([08](08-clipboard-propagation.md))

사용자 요구: 한쪽에서 복사하면 다른 PC로 자동 전파(LAN+원격), **파일은 내용이 아닌 목록**. 추가로 **Android·iOS 수신을 최하순위 목표**에 포함.

**함정 3개를 먼저 세웠다.**

1. **파일 목록은 상대 PC에서 깨진다** — `D:\작업\보고서.xlsx`는 B에 없다. 붙여넣으면 **조용히 실패**한다. 구현 버그가 아니라 요구에 내재한 성질이라 먼저 결정이 필요하다. 권장 = **적응형**(경로 실재 확인 → 있으면 파일 객체, 없으면 텍스트 + UI 표시). NAS·공유 폴더 환경에서는 그대로 완전 동작한다.
2. **자동 덮어쓰기가 상대의 작업을 파괴한다** — 이 카테고리 불만 1순위. 다만 **W-1(덮어쓰기 전 원본을 기록에 저장) + W-3(되돌리기)** 를 붙이면 사용자 요구대로 ②(자동 덮어쓰기)를 기본값으로 둬도 안전하다고 판단.
3. **에코 루프** — 자동 전파 + 클립보드 감시가 있으면 **반드시** 발생. `origin` 기기 id로 재전파 차단(본체) + 쓰기 직전 해시 억제(보험). OS가 "우리가 쓴 것"과 "사용자가 쓴 것"을 구별해 주지 않아 둘 다 필요하다.

**LAN vs 원격 분리**: 원격 이미지는 **메타 먼저 + 붙여넣을 때 본문 가져오기**. `blob_id` 내용 주소 덕에 이미 가진 항목은 가져오기가 통째로 생략된다 — [06](06-storage-design.md)의 중복 제거 규칙이 여기서 또 배당금을 냈다.

**모바일 조사 결과**: *"전달받도록"* 이라는 한정이 정확했다. **iOS는 백그라운드 클립보드 읽기 불가, Android는 API 29부터 차단** — 자동 캡처는 원리적으로 안 된다. 모바일은 "클립보드 매니저"가 아니라 **"받은 항목 목록 + 탭하면 복사"** 가 된다. 최하순위인 진짜 이유는 기능 크기가 아니라 **UI를 한 벌 더 만들어야 하기 때문**이고, iOS APNs 때문에 *"서버 코드 변경 0"* 도 모바일에서는 깨진다.

## 4차 — 기기 랑데부 ([07](07-device-rendezvous.md))

질문: *"두 PC가 릴레이에 동시 접속했을 때 같은 사람(UserId)임을 확인하는 기법은?"*

**결론**: 서버는 확인하지 않는다. **① 랑데부(서버) → ② Noise 인증(종단) → ③ DeviceList 소속(종단)** 3단이고, *"같은 사람인가"* 는 **③에서만** 답해진다. 서버가 UserId를 알면 S-3(봉투 원리)·R-18(영구 재식별자)이 무너지고 릴레이가 관리 서버로 미끄러진다.

**실코드에서 설계를 결정하는 제약을 찾았다.**

```rust
// crates/nexa-beepd/src/lib.rs:127, 459
rids: Mutex<HashMap<Rid, ConnId>>,            // 1 RID = 1 연결
for r in &rids { map.insert(*r, conn_id); }   // 나중 등록이 앞을 덮어쓴다
```

→ *"UserId에서 공유 랑데부 ID 하나를 파생해 전 기기가 거기서 만난다"* 는 매력적인 안이 **현재 서버에서 그냥 깨진다**(뒤에 붙은 기기가 앞의 기기를 지움). **기기별 회전 RID**로 가고 상대 RID는 DeviceList에서 얻은 PeerId로 계산 — **서버 코드 변경 0** 유지.

**또 하나**: beep roster(`C2s::Announce` / `S2c::PeerUp { peer: PeerId }`)는 **공개키 원본을 서버와 접속자 전원에게 노출**한다. 편해 보이지만 다중 기기용으로 쓰면 R-18이 그대로 터진다 — 옵트인 공개 모드 전용이다.

**동시 접속 문제**: `nexa-beepd` 주석이 *"버퍼가 아니라 파이프다(양쪽 동시 접속일 때만 흐른다)"* 라고 명시 — **오프라인 큐가 없다**. 사용자가 질문을 "동시에 접속했을 때"로 시작한 것이 정확한 직감이었다. 그리고 **glare(양쪽 동시 Open)에 대한 타이브레이크가 beep에 없어** 우리가 정해야 한다 → **PeerId 사전순으로 작은 쪽이 initiator**(추가 왕복 0). 에폭 경계는 `rids_around` 3개 등록으로 이미 해결돼 있다.

## 3차 — 저장 설계 ([06](06-storage-design.md))

질문: *"DB화가 좋을까, 파일 Serializing으로 충분할까?"*

접근 패턴을 세어 보니 **join도 트랜잭션 경합도 복잡한 질의도 없다** — 쓰기는 끝에 붙이기(append), 삭제는 앞에서 자르기, 검색은 훑기. **DB가 잘하는 문제가 아니라 로그가 잘하는 문제**다.

**결론: 파일 직렬화 + 3규칙**(인덱스/blob 분리 · append-only 세그먼트 · 내용 주소 blob).

**수치 근거**: 인덱스 레코드 ≈ 270B → 1만 항목 = **2.7MB RSS**. 전체를 메모리에 상주시킬 수 있어 **검색이 메모리 순회(1ms 미만)** 가 되고, 그래서 **FTS 색인이 필요 없어진다**. 10만 항목이면 27MB로 예산을 혼자 다 먹으므로 기본 상한 1만을 권했다.

**SQLite를 안 쓰는 결정적 이유는 암호화다** — 디스크를 봉인하면 암호문에 인덱스도 FTS도 못 건다. SQLite를 링크하고도 검색은 결국 복호 후 스캔이라 **DB를 쓰면서 DB의 이점을 못 쓴다**. 경쟁사(Ditto·EcoPaste·Maccy)가 전부 SQLite인 것은 **전부 암호화를 안 하기 때문**이다. 뒤집혀야 할 조건(10만+ 상시, 복합 질의, 암호화 포기)을 §3-1에 정직하게 적었고, **저장 계층을 트레이트 뒤에** 두어 교체 가능하게 하자는 D-1-f를 달았다.

## 2차 — 다중 기기 공유 ([05](05-multi-device-sharing.md))

질문: *"beep의 릴레이·컨텐츠 서버로 다수 장비 간 클립보드 공유가 가능한가? 별도 릴레이 서버를 만들어야 하나?"*

**beep이 이미 답을 적어 놨다.** ADR-0007 §1 첫 줄: *"처음 질문은 '릴레이(서버 모드)로 되나'였다. **답은 아니다.**"* 릴레이는 **"닿는가"** 를 풀지 **"같은 사람인가"** 를 풀지 않는다 — PeerId는 기기가 생성한 정적 공개키라, 릴레이를 붙여도 PC 2대는 여전히 서로 다른 두 노드다. 필요한 건 **UserId 1:M PeerId(ADR-0007)** 이고 beep에서도 v2 미구현이다.

**별도 릴레이 서버는 불필요**: 릴레이는 `[RID][채널][길이][암호문]`만 다루므로 그 암호문이 채팅인지 클립보드인지 서버가 알 이유가 없다 → `nexa-beepd` **재사용, 서버 코드 변경 0**. 실제 결정 지점은 서버가 아니라 **`nbeep-relay`를 어떻게 참조하느냐**(D-8)다. ADR-0013 §9의 교훈(*"괴롭히는 건 빌드 시간이 아니라 와이어 포맷 어긋남"*)과 가드레일 W-1~W-4를 그대로 가져왔다.

**부수 수확**: ADR-0013 §5-9의 **"blob 1개 + 봉투 N개"** 가 다중 기기 클립보드에 그대로 맞는다. 5MB 이미지 4대 → 20MB가 5MB로 줄고, `blob_id = H(암호문)` 덕에 **중복 제거가 공짜**다 — 클립보드는 같은 것을 반복 복사하는 도구라 이득이 크다.

**사용자 방향**(*"전송은 beep처럼 봉인, 로컬은 해제해 관리"*)을 검토하며 **두 층이 섞여 있음**을 지적했다. 메모리 평문은 당연히 필요하지만 **디스크까지 평문이면 지금 쓰는 CopyQ보다 후퇴**하고, 동기화를 켜면 평문 사본이 기기 수만큼 늘어 노트북 분실 1회 = 전 기기 이력 유출이 된다. **①네트워크 봉인 / ②메모리 평문 / ③디스크 봉인(기본 켜짐)** 3층 분리를 제안 → D-9.

**동기화 두 축 확정**(사용자): 같은 UserId = 자동 연동, 신뢰 기기 = 등록 후 공유. ⚠️ **②를 자동 미러링하면 안 된다**고 지적했다 — beep에서 신뢰한 상대는 *내가 보낸 것*만 받지만, 클립보드를 같은 규칙으로 미러링하면 **복사한 모든 것(비밀번호 포함)이 상대에게 흐른다**. 그래서 ②는 "동기화"가 아니라 **"공유"**(기본 무전파 · 명시적 전송 또는 공유 보드 옵트인)로 설계했다. **내 기기끼리는 동기화, 남과는 공유.**
