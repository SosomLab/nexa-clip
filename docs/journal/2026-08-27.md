## 3차 — Windows 클립보드 감시(T-14b) · ★ 첫 실행에서 버그 넷이 나왔다

★ **제품이 처음으로 "동작"한다.** 복사하면 잡힌다.

```
$ nexa-clip watch
클립보드 감시: ok (win32-listener)

[3]
  종류   : Text
  표현   : 6개 (남김 6개)
           DataObject                                 8 B
           CF_UNICODETEXT                             18 B
           …
  미리보기: 한글 평문 확인
```

### 1. 왜 전용 스레드인가

`AddClipboardFormatListener`는 **창**에 붙고 알림은 **그 창의 메시지 큐**로 온다.
UI 이벤트 루프에 얹으면 감시가 창 생명주기에 묶여서 **설정 창을 닫으면 감시가 멎는다**.

★ **메시지 전용 창**(`HWND_MESSAGE`)을 **자기 스레드**에 띄웠다. 화면에 없고, 입력도 안 받고,
`WM_CLIPBOARDUPDATE`만 받는다. `GetMessageW`가 블록하므로 **유휴에서 CPU를 안 쓴다**(DR-9 예산).

`start`는 스레드가 창을 실제로 세운 것을 **확인하고 나서** `Ok`를 준다 —
안 그러면 *"start는 성공인데 아무 일도 안 일어나는"* 상태가 된다.

### 2. ⚠️ 손대기 전에 알아야 했던 두 가지

| | |
|---|---|
| **클립보드는 한 번에 한 프로세스만 연다** | 복사 직후엔 **복사한 앱이 아직 쥐고 있다**. 한 번 실패하고 포기하면 *"가끔 복사가 안 잡힌다"* 는 유령 버그가 된다 → 5·10·15…ms로 물러섰다 재시도 |
| **핸들 포맷을 `GlobalLock`으로 읽으면 안 된다** | `CF_BITMAP`은 `HBITMAP`, `CF_ENHMETAFILE`은 `HENHMETAFILE`이다. `GlobalSize`를 부르면 엉뚱한 값이 나오거나 죽는다 → 이름만 담는다(분류는 이름만 보므로 지장 없다) |

### 3. ★ 첫 실행에서 **버그 넷**이 나왔다 — 전부 조용히 틀리는 종류

이게 이번 작업의 진짜 소득이다.

#### ① `CF_UNICODETEXT`는 UTF-16LE다

```
미리보기: c a r g o   r u n   - p   n e x a - c l i p
```

UTF-8로 읽으니 NUL이 공백처럼 끼었다. ★ **한글은 아예 디코드에 실패해 통째로 사라졌다.**
ASCII는 조용히 망가지고 한글은 조용히 없어진다 — **둘 다 오류를 안 낸다**.

`decode_plain`으로 포맷별 인코딩을 정하고, `plain_rank`로 **정확히 풀리는 것부터** 보게 했다.
⚠️ `CF_TEXT`·`CF_OEMTEXT`는 시스템 코드 페이지라 우리가 못 푼다 — Windows가 텍스트가 있으면
`CF_UNICODETEXT`를 자동 합성하므로 그쪽이 먼저다. **순서를 뒤집으면 한글이 깨진다.**

#### ② `DataObject` 하나가 텍스트를 리치로 만들었다

PowerShell 한 줄 복사가 `RichText`로 찍혔다. 범인은 **8바이트짜리 `DataObject`** —
*"모르는 포맷 = 벤더"* 규칙에 그대로 걸렸다.

★ [D-75](../27-capture-cases.md)가 *"곁다리 목록은 실기에서 자란다"* 고 적어 둔 그 자리다.
설계 때 예상한 위험이 **첫 실행에서 바로** 터졌다.

#### ③ 그런데 고쳐도 여전히 리치였다 — `CF_OEMTEXT`

곁다리를 채웠는데도 안 됐다. ⚠️ **`CF_OEMTEXT`가 평문 목록에 없었다.**
Windows는 텍스트를 `CF_UNICODETEXT`·`CF_TEXT`·`CF_OEMTEXT` **셋으로 함께** 올리는데
셋째를 몰랐으니 벤더로 세어졌다.

#### ④ ★ "벤더면 무조건 리치"가 틀렸다

.NET `System.Drawing.Bitmap`으로 복사한 **순수 그림**이 `RichText`로 찍혔다.

설계 초안은 *"PPT 도형에도 `CF_DIB`가 있으니 벤더가 비트맵보다 먼저"* 였다. 맞는 말이지만
**너무 넓었다** — 그림 전용 벤더까지 리치로 끌고 갔다.

★ **글이 하나도 없는데 "서식 있는 글"이라고 하면 거짓말이다.** 갈래를 하나 넣었다:

```
③ 벤더가 있다
     ├ 평문이 함께 있다  → RichText   (PPT 도형 · Excel 범위)
     ├ 아니고 비트맵     → Image      ★ 그림 전용 벤더
     └ 둘 다 없다        → RichText   (순수 개체)
```

### 4. 설계가 코드를 만나며 바뀐 것

| # | 무엇 | 왜 |
|:--:|---|---|
| **1** | `ClipSnapshot.reps`가 `Representation` → **`RawRep`** | ★ 감시 계층은 `blob_id`(암호문 해시)를 **만들 수 없다** — 키는 저장 계층이 갖는다. **모르는 것을 채우게 만들지 않는다** |
| **2** | `capture`가 **`RepInfo` 제네릭**으로 | 판정에 필요한 건 **이름과 크기뿐**이다. 그러면 `RawRep`도 `Representation`도 그대로 들어간다 |
| **3** | `Captured.reps` → **`keep: Vec<usize>`** | 20MB짜리를 판정 한 번에 한 벌 더 만들 이유가 없다 |
| **4** | `PreviewMissing::ThumbMissing` 신설 | 썸네일이 아직 없는 것을 `TooLarge`로 뭉뚱그리면 **사용자가 원인을 잘못 짚는다** |

### 5. `watch` 명령 — 진단이 제품과 **같은 함수**를 쓴다

★ 진단용으로 따로 판정하지 않는다. `watch`는 실제 저장 경로가 쓸 `capture()`를 그대로 부른다 —
**여기서 맞게 보이면 제품에서도 맞다.** 버려진 표현에는 `✂`를 찍어 **조용히 사라지지 않게** 했다.

## 2차 — ⚠️ Retina에서 **글자만 작아져 있었다** · macOS K-1 통과

### 1. 증상 — 레이아웃은 2배, 글자는 1배

사용자가 mac 설정 창 스크린샷을 보내 왔다. 행 높이·사이드바 폭·여백은 정상인데
**글자만 깨알**이었다. *"beep 때도 겪었던 화면 비율 문제"* 라는 제보와 함께.

### 2. 원인 — 한 줄이 빠져 있었다

`RasterCtx`는 배율을 **글자 크기에 곱해서** 그린다. 그런데 호스트가 그 값을 안 넘겼다.

```rust
let mut dc = RasterCtx::new(&mut gfx, &self.font);   // 배율이 기본 1.0으로 남는다
```

위젯에는 `set_scale(2.0)`을 줬으니 **레이아웃만 2배**가 됐다.

`nexa-beep`를 확인하니 같은 자리에서 **`.with_scale(entry.scale)`를 부르고 있었다**(`app.rs:14055`).
이식하면서 그 한 줄이 빠진 것이다.

★ **Windows(배율 1.0)에서는 우연히 맞아 보인다.** 그래서 한쪽 OS에서만 조용히 틀렸고,
mac에서 실제로 띄워 보기 전까지 아무도 몰랐다. 1차의 *"OS 분기 코드는 그 OS에서
한 번은 빌드되기 전까지 '작성됨'이지 '됨'이 아니다"* 와 같은 이야기다 —
**빌드를 넘어 화면까지** 그렇다.

### 3. 조치 — 테스트가 아니라 **구조**로

```rust
pub fn new(surface: &mut Surface, font: &Font, scale: f32) -> Self
```

배율을 **필수 인자**로 승격했다. 빌더 옵션(`with_scale`)이면 또 빠뜨릴 수 있지만
**인자는 컴파일러가 강제**한다. `with_scale`은 없앴다 — 방법이 둘이면 하나를 잊는다.

⚠️ 테스트로 막을 수도 있었지만 *"렌더 결과가 배율에 맞는가"* 는 픽셀을 봐야 하는 검사다.
**애초에 못 쓰게 만드는 쪽**이 싸고 확실하다.

### 4. macOS K-1 통과 (사용자 실기)

```
cargo run -p nexa-clip -- spike-paste --wait 8
→ 손쉬운 사용에 iTerm 추가 후 Sublime Text 붙여넣기 성공
```

★ **Windows와 달리 복원 경로까지 실제로 돌았다.** mac은 스파이크를 띄운 터미널이
프런트모스트였다가 대상 앱으로 넘어가므로 `NSRunningApplication` 활성화가
**우회 없이 정상 경로로** 실행된다(Windows에서 `[3] 포커스 탈취: 실패` 로 건너뛴 구간).

⚠️ **권한 주체가 우리 바이너리가 아니라 터미널이다.** `cargo run`으로 돌리면
iTerm이 권한을 갖는다. 배포본(`.app` 번들)에서는 **번들 자체를 손쉬운 사용에 추가**해야 하고
그때 권한이 다시 물어진다 — **개발 중 통과가 배포본 통과를 뜻하지 않는다**(→ T-9d).

## 1차 — macOS 빌드가 깨져 있었다 · 설정 읽기 mac 실기 확인

### 1. ⚠️ `nclip-plat`이 macOS에서 한 번도 컴파일된 적이 없었다

`cargo build --workspace`가 mac에서 **E0133 × 13**으로 죽었다. 위치는 K-1 스파이크(16차 · `dddd478`)의
mac 전용 `paste::imp::appkit` — `cls`·`sel`·`send0`·`send0_i32`·`send1_bool`.

원인은 단순하다. `nclip-plat/src/lib.rs`가 **`#![forbid(unsafe_op_in_unsafe_fn)]`** 인데, 저 다섯 `unsafe fn`이
본문에서 `unsafe {}` 블록 없이 FFI를 호출했다. Windows 세션에서 작성돼 **`cfg(target_os = "macos")` 안쪽은 컴파일러가
본 적이 없었다.** CI 매트릭스에 `macos-latest`가 있으니([18 §6](../18-build-and-test.md)) 그 잡도 빨간 상태였을 것이다.

수정은 본문을 `unsafe { … }`로 감싼 것뿐 + `unreachable_pub` 경고 2개(`pub` → `pub(super)`).
★ **교훈** — OS 분기 코드는 **그 OS에서 한 번은 빌드**되기 전까지 "작성됨"이지 "됨"이 아니다.
[21](../21-manual-test.md)의 ☐/⏳ 구분과 같은 얘기다.

### 2. T-12c 설정 읽기 — macOS ✅

17차의 점검 화면 수정이 mac에서도 그대로 맞는지, 저장본 두 상태로 돌렸다.

| 상태 | `settings` | view | theme | max items | tray |
|---|---|---|---|---|---|
| 파일 없음 | `target/debug/data/settings.cfg (아직 없음 — 기본값)` | Compact | system | 1000 | 8 |
| 저장본 | `… (저장본 사용)` | **Rich** | **dark** | **2500** (후보에 없는 직접 입력값) | **15** |

포터블 우선([DR-33](../10-decision-record.md))이 mac에서도 실행 파일 옆 `data/`를 골랐다 — `target/debug`는
`is_replaced_on_upgrade`에 걸리지 않는다(맞다 — `.app` 번들도 Homebrew keg도 아니다).

`nexa-clip settings`도 뜬다 — `폰트: Apple SD Gothic Neo · 설정 항목 21개`. 창 조작(값 변경 → 재시작 · 미지 키
보존 · 숫자 표시 · hover 페이드)은 **사람 손이 필요**해 [21](../21-manual-test.md) ⏳로 남긴다.

`paste inject : ok (mac-cgevent)` — K-1 mac 검증([21 §2-4](../21-manual-test.md))도 사람 손이 필요하다
(손쉬운 사용 권한 + 대상 앱 클릭).

235 테스트 · fmt · clippy `-D warnings` 클린 — **이번엔 mac에서**.
