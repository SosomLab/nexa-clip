## 7차 — ★ `WM_CLIPBOARDUPDATE`가 안 오는 일이 실제로 있다 · 하트비트 안전망

⑨(타이머 재시도)를 넣은 빌드에서도 사용자 실기: **첫 탐색기 복사는 잡히고
그다음부터 안 잡혔다**. 사용자가 PC를 넘겨줘 **직접 재현·조사**했다.

### 1. 재현 — 이벤트 자체가 안 온다

감시 인스턴스를 파일 출력으로 띄워 두고 시나리오를 자동화했다:

| 시나리오 | 결과 |
|---|---|
| 연속 텍스트 3회(`Set-Clipboard`) | ✅ 전부 즉시 |
| 게시 직후 클립보드 1.5초 잠금(비동기 플러시 흉내) | ✅ **타이머 재시도가 잡았다**(⑨ 검증) |
| 모의 셸 포맷 연속 2회 | ✅ 전부 |
| ★ **실제 탐색기 창 활성화 + `Ctrl+C`** | ❌ **유실** — 클립보드는 바뀌었는데(`peek` 확인) 이벤트가 안 왔다. 직후 텍스트 복사는 즉시 잡힘(스레드 생존) |

진단 출력(`NEXA_CLIP_DIAG=1`)을 넣고 재시도하니 **이번엔 잡혔다** — 유실은 **간헐적**이다.
⑨의 재시도는 *이벤트가 온 뒤* 의 실패만 구제한다 — **이벤트가 아예 안 오면 손댈 수 없었다**.

원인 후보는 특정 못 했다(같은 기기에 CopyQ·Windows 클립보드 기록 등 다른 리스너가
상주한다 — 관련 가능성만 기록). ★ **원인을 못 밝혀도 증상은 막아야 한다.**

### 2. 조치 — 일련번호 하트비트 (2초)

`GetClipboardSequenceNumber`는 **클립보드를 열지 않는** 조회 하나다. 2초마다 이 값만
마지막 처리 번호와 비교하고, **다를 때만** 실제로 읽는다.

- 유휴 비용 = 2초당 시스템 호출 1회(DR-9 예산에 무해) — 폴링이 아니라 **유실 안전망**이다.
- 이벤트 경로가 먼저 처리하면 번호가 같아 **중복이 생기지 않는다**(try_deliver의 seq 중복 차단이 이중 방벽).
- 시작 시 현재 번호를 기준점으로 잡는다 — 안 하면 첫 하트비트가 `read_now`가 이미 보여 준
  기존 내용을 새 항목처럼 배달한다.

### 3. 검증 — 실제 탐색기 `Ctrl+C` × 3 왕복

탐색기 창을 활성화해 `^C`를 보내고 사이사이 텍스트를 끼워 6회 왕복 —
**전부 잡혔다**(diag로 이벤트/하트비트 경로 구분 확인). 1회차 `^C`는 이벤트·하트비트가
**둘 다 침묵**했는데, 이는 유실이 아니라 **키가 창에 안 들어간 것**이다(두 독립 경로의
동시 침묵 = 클립보드 번호가 안 움직였다는 교차 증거).

### 4. 진단 스위치 — `NEXA_CLIP_DIAG=1`

수신/전달/중복/열기 실패/하트비트를 stderr로 찍는다. 다음에 *"안 잡힌다"* 가 나오면
이 출력이 **"안 왔다"와 "와서 버려졌다"를 구분**해 준다.

**실측**: 301 테스트 · clippy `-D warnings` · fmt 클린 · 실기 왕복 6회 통과.

## 6차 — ★ Edge 암호 관리자는 표식을 안 붙인다 (실기 확인)

사용자가 `edge://wallet/passwords`(Microsoft 암호 관리자)에서 암호 복사를 실기했다.

```
[2] 종류: Text · 출처: msedge · 표현 6개
    CF_UNICODETEXT · Chromium internal source RFH token ·
    Chromium internal source URL · CF_LOCALE · CF_TEXT · CF_OEMTEXT
    미리보기: (비밀번호 평문)
```

**`ExcludeClipboardContentFromMonitorProcessing`이 없다.** 비밀번호가 평문 `Text`로 잡혔다.

- 우리 결함이 아니다 — 표식이 **있으면** 막는 것은 5차에서 모의 클립보드로 검증했다(⑩).
  Edge가 안 붙이는 것이고, 같은 이유로 **Win+V 클립보드 기록·클라우드 클립보드에도 남는다**.
- ★ **함의: FR-S-1(표식 존중)만으로는 비밀번호를 다 못 막는다** → **D-79** 신설:
  ① 제외 앱(FR-S-2·T-21) ② `Chromium internal source URL` **내용**이 `edge://wallet`·
  `chrome://password-manager`면 민감 판정 — 출처 URL이 캡처에 이미 담겨 온다.
- 전용 관리자(1Password·KeePass 등)의 표식 실기는 **보유 시에만**(보류).

## 5차 — 3차 훑기(Word·탐색기)가 결함 셋을 또 잡았다 · 데모 두부 수정

사용자가 2차 목록(Word · 탐색기 잘라내기 · Outlook · 비밀번호 관리자)을 훑었고,
동시에 창 점검 4건(포커스 복원 재검증 · 설정 쓰기 · 숫자 표시 · 데모)을 넘겨줬다.

### 1. 실기 결과 — Word는 맞았고, 탐색기에서 셋이 나왔다

**Word 서식 문단 2건 ✅** — `RichText` · 표현 18개 · `Embed Source`/`Native` 유지
(4차에 박은 *"곁다리가 아니다"* 방향이 실기로 확인됐다). Outlook은 미사용으로 보류.

| # | 증상 | 원인 | 조치 |
|:--:|---|---|---|
| **⑧** | ★ 탐색기 **잘라내기**가 `Object` | **`CF_HDROP`이 열거되지 않는다**(지연 렌더링). 파일 목록의 본체 `Shell IDList Array`(PIDL 묶음)를 곁다리로 치니, 남은 미지 셸 포맷(`DataObjectAttributes`·`AsyncFlag` 등)이 벤더로 세어졌다 | `Shell IDList Array` → **파일 포맷**([`is_files_format`](../../crates/nclip-core/src/capture.rs)) |
| **⑨** | ★ 탐색기 **복사가 아예 안 잡힘** | 탐색기는 비동기 플러시(`AsyncFlag`) 동안 클립보드를 계속 쥔다 → `open_with_retry` 275ms 초과 → **`wnd_proc`가 실패를 조용히 버림** + `WM_CLIPBOARDUPDATE`는 **병합**되어 다시 안 온다 | ★ **타이머 재시도**(`SetTimer` 200ms × 15회 ≈ 3초) — 놓친 변화를 따라잡는다 |
| **⑩** | `watch`/`peek`가 **민감 표식 무시** | `read_concealed`가 값을 채우는데 **아무 데서도 안 읽었다** — 문서 표에는 "안 늘어난다"고 적혀 있었지만 코드는 그대로 찍었다 | `report`가 `concealed`면 **내용 없이 `(민감 표식 …)` 한 줄만** — 침묵이 아니라 마스킹(점검자가 "막힘"과 "놓침"을 구분해야 한다) |

⑧과 ⑩은 **모의 클립보드로 자가 검증**했다 — 실기 [3]의 포맷 셋 7개를 그대로 재현해
`Files` 판정 확인, 표식+비밀번호를 올려 마스킹 확인. ⑨의 실제 타이밍은 실기 재점검 대상.

⚠️ ⑨가 제일 뼈아프다 — `watch_win.rs` 머리말에 *"실패를 그대로 흘리면 유령 버그가 된다"* 고
**적어 놓고는** `open_with_retry`가 실패하는 경로를 조용히 버리고 있었다. 경고를 문서에만
두면 언젠가 깨진다는 것을 우리가 다시 증명했다.

### 2. 잘라내기/복사 실기 캡처를 박제 — [19] Word · [20] 탐색기 잘라내기

[`real_clipboard_captures.rs`](../../crates/nclip-core/tests/real_clipboard_captures.rs)에 추가.
[20]은 `CF_HDROP` 없는 7개 포맷 셋 그대로다 — 이 판정이 다시 `Object`로 돌아가면 즉시 깨진다.

### 3. 창 점검 4건 (사용자 실기)

| 항목 | 결과 |
|---|---|
| **T-9b'** 포커스 복원 재검증(탈취 경로) | ✅ 통과 |
| **T-12c3** 설정 쓰기(값 변경 → 재시작 유지) | ✅ 통과 |
| **T-12d5** 개수 설정 숫자 표시 | ✅ 통과 |
| **T-12b2** 렌더 데모 | 크기·모양 양호 · ⚠️ **두부(□) 발견** |

### 4. ⚠️ 데모 두부 — 의도가 아니라 **폰트에 없는 글자**였다

데모 데이터가 이모지 아이콘(`📄`·`📁`·`🎨`·`🔒`)과 `↵`(U+21B5)를 썼다.
래스터라이저는 시스템 폰트 **한 벌**만 쓰고 **폴백이 없어서** 맑은 고딕에 없는 글리프는
.notdef(□)로 그려진다 — `▣`(U+25A3)만 KS X 1001에 있어 살아남았고, 그래서
스크린샷·PPT 행만 아이콘이 보였다.

KS X 1001 도형 문자로 교체했다(`▤` 문서 · `▦` 폴더 · `◆` 색 · `¶` 줄바꿈 표식 ·
푸터 `🔒` 제거). ★ **제품 아이콘은 글리프로 안 그린다**(T-18b에서 직접 그린다) —
글리프 아이콘은 폰트 커버리지에 인질로 잡힌다.

**실측**: **301 테스트** · clippy `-D warnings` 클린 · 자가 검증 2건(⑧·⑩) 통과.

## 4차 — 실기 18건이 설계 결함 셋을 더 잡았다 · `ClipKind::Object`

사용자가 **실제 업무 자료**로 `watch`를 훑었다 — PPT 도형·표·글상자, Excel 범위,
Edge 웹/평문, VS Code, Greenshot, CopyQ. 18건.

★ **설계로는 안 보이던 것이 또 셋 나왔다.** 3차의 넷과 합쳐 **일곱**이다.

### 1. ★ PPT 도형이 `Image`로 분류됐다 — 우리 분류에 **자리가 없었다**

```
[1] 종류: Image · 출처: POWERPNT
    Art::GVML ClipFormat · PowerPoint 12.0 Internal Shapes
    PNG · JFIF · GIF · CF_DIB · CF_DIBV5 …   (평문 없음)
```

3차에서 *"글 없는 벤더 = 그림"* 으로 고친 게 **너무 넓었다**. .NET 비트맵을 잡으려다
**PPT 도형까지 끌고 갔다.**

PPT 도형은 이미지도 서식 있는 글도 아니다:

| 뭐라고 하면 | 왜 틀린가 |
|---|---|
| `Image` | ★ **붙여넣으면 편집 가능한 도형**이라는 사실이 가려진다. "이미지" 필터에 도형이 딸려 온다 |
| `RichText` | 글이 **하나도 없는데** "서식 있는 글"이라고 한다 |

**`ClipKind::Object`를 새로 뒀다.** 도형·차트처럼 **그림도 글도 아닌 앱 개체**다.
미리보기는 함께 온 비트맵을 쓰고([27 §2-3](../27-capture-cases.md) — Office가 넣어 준다),
붙여넣기는 원본 표현을 전부 되돌린다.

⚠️ **붙여넣기 모드도 손봤다** — `Object`는 `Original` 하나뿐이다.
평문으로 낮추면 **아무것도 안 나온다**.

★ **경계가 실제로 잘 갈린다** — 같은 훑기 안에서:

| 실기 | 표현의 특징 | 종류 |
|---|---|:--:|
| PPT 도형 | `Art::GVML` + 그림들, **평문 없음** | `Object` |
| PPT **표** | `Art::Table` + **`HTML Format`** | `RichText` |
| PPT **글상자** | `Art::Text` + HTML + RTF + **평문** | `RichText` |
| **Greenshot** | 진짜 벤더 없음 · `PNG`+`CF_DIB`뿐 | `Image` |

같은 앱에서 온 셋이 서로 다르게 판정된다. **하나로 뭉뚱그리면 셋 다 틀린다.**

### 2. `JFIF`·`GIF`·`image/svg+xml`이 **벤더로 세어지고 있었다**

PPT는 그림을 **네다섯 벌** 올린다 — `PNG` · `JFIF` · `GIF` · `image/svg+xml` · `CF_DIB` · `CF_DIBV5`.
그런데 우리 그림 목록에는 `PNG`와 `CF_DIB` 계열뿐이라 **나머지가 전부 벤더로 세어졌다.**

`JFIF`는 그냥 JPEG다. 이름표가 좁아서 판정이 흔들리고 있었던 것이다.

### 3. ★ **표현 0개짜리 항목**이 만들어졌다

```
[14] 종류: Text · 출처: EXCEL · 표현: 0개 · 미리보기: 미리보기 없음
[9]  종류: RichText · 출처: rdpclip
     DataObject · Terminal Services Private Data · Ole Private Data
```

[14]는 **Excel이 지연 렌더링으로 클립보드를 다시 채우는 순간**에 읽힌 것이고,
[9]는 원격 데스크톱이 **자기 표식만** 올린 것이다.

목록에 빈 줄이 쌓이면 사용자는 **제품이 고장 났다고 읽는다.**
게이트에 `has_content` 검사를 넣었다.

⚠️ **순서가 중요하다** — *"다음 1건 무시"* **보다 앞**이어야 한다.
빈 스냅숏이 예약을 소모해 버리면 **정작 다음 진짜 복사가 저장된다.** 테스트로 박았다.

### 4. ✅ 예측이 맞았다 — Edge 평문

3차 끝에 *"브라우저 입력창에서 맨 텍스트를 복사하면 Chromium 표식만 딸려 와서
평문이 리치로 분류될 것"* 이라 적고 미리 고쳤는데, **실기 [16]이 정확히 그 케이스**였다.

```
[16] 종류: RichText · 출처: msedge
     CF_UNICODETEXT · Chromium internal source RFH token · Chromium internal source URL …
```

고치기 전 빌드라 `RichText`로 찍혔고, 지금 규칙에서는 `Text`다.

### 5. ★ 실기 회귀 박제

18건을 [`tests/real_clipboard_captures.rs`](../../crates/nclip-core/tests/real_clipboard_captures.rs)에
**포맷 이름 그대로** 넣었다.

분류 규칙은 앞으로도 손댈 일이 생긴다. 그때마다 *"PPT 도형은 어떻게 되지?"* 를 다시
실기로 확인할 수는 없다. ★ **실제 클립보드가 준 이름 목록**을 두면 규칙을 고칠 때
**무엇이 깨지는지 즉시 보인다**.

⚠️ 파일에 *"이름을 보기 좋게 다듬지 말 것"* 을 적어 뒀다 — 다듬는 순간 실기 기록이
아니라 창작이 된다.

⚠️ 반대 방향 테스트도 넣었다 — **Excel의 `Embed Source`·`Native`는 곁다리가 아니다**.
곁다리 목록을 넓히다 보면 **개체 본문을 버리게 된다**. 이름에 "Source"가 들어간다고
규칙으로 거르면 `Embed Source`가 날아간다.

### 6. `peek` — 한 번만 보는 명령

`watch`는 계속 떠 있어야 하는데 *"방금 복사한 게 뭐로 잡혔나"* 만 보고 싶을 때가 잦았다.
감시를 걸지 않으므로 **`watch` 세션과 함께 써도 된다**.

## 3차 — Windows 클립보드 감시(T-14b) · ★ 첫 실행에서 버그 넷이 나왔다

★ **제품이 처음으로 "동작"한다.** 복사하면 잡힌다.

```
$ nexa-clip watch
클립보드 감시: ok (win32-listener)

[3]
  종류   : Text
  표현   : 6개 (남김 6개)
           DataObject                                 8 B
           CF_UNICODETEXT                             18 B
           …
  미리보기: 한글 평문 확인
```

### 1. 왜 전용 스레드인가

`AddClipboardFormatListener`는 **창**에 붙고 알림은 **그 창의 메시지 큐**로 온다.
UI 이벤트 루프에 얹으면 감시가 창 생명주기에 묶여서 **설정 창을 닫으면 감시가 멎는다**.

★ **메시지 전용 창**(`HWND_MESSAGE`)을 **자기 스레드**에 띄웠다. 화면에 없고, 입력도 안 받고,
`WM_CLIPBOARDUPDATE`만 받는다. `GetMessageW`가 블록하므로 **유휴에서 CPU를 안 쓴다**(DR-9 예산).

`start`는 스레드가 창을 실제로 세운 것을 **확인하고 나서** `Ok`를 준다 —
안 그러면 *"start는 성공인데 아무 일도 안 일어나는"* 상태가 된다.

### 2. ⚠️ 손대기 전에 알아야 했던 두 가지

| | |
|---|---|
| **클립보드는 한 번에 한 프로세스만 연다** | 복사 직후엔 **복사한 앱이 아직 쥐고 있다**. 한 번 실패하고 포기하면 *"가끔 복사가 안 잡힌다"* 는 유령 버그가 된다 → 5·10·15…ms로 물러섰다 재시도 |
| **핸들 포맷을 `GlobalLock`으로 읽으면 안 된다** | `CF_BITMAP`은 `HBITMAP`, `CF_ENHMETAFILE`은 `HENHMETAFILE`이다. `GlobalSize`를 부르면 엉뚱한 값이 나오거나 죽는다 → 이름만 담는다(분류는 이름만 보므로 지장 없다) |

### 3. ★ 첫 실행에서 **버그 넷**이 나왔다 — 전부 조용히 틀리는 종류

이게 이번 작업의 진짜 소득이다.

#### ① `CF_UNICODETEXT`는 UTF-16LE다

```
미리보기: c a r g o   r u n   - p   n e x a - c l i p
```

UTF-8로 읽으니 NUL이 공백처럼 끼었다. ★ **한글은 아예 디코드에 실패해 통째로 사라졌다.**
ASCII는 조용히 망가지고 한글은 조용히 없어진다 — **둘 다 오류를 안 낸다**.

`decode_plain`으로 포맷별 인코딩을 정하고, `plain_rank`로 **정확히 풀리는 것부터** 보게 했다.
⚠️ `CF_TEXT`·`CF_OEMTEXT`는 시스템 코드 페이지라 우리가 못 푼다 — Windows가 텍스트가 있으면
`CF_UNICODETEXT`를 자동 합성하므로 그쪽이 먼저다. **순서를 뒤집으면 한글이 깨진다.**

#### ② `DataObject` 하나가 텍스트를 리치로 만들었다

PowerShell 한 줄 복사가 `RichText`로 찍혔다. 범인은 **8바이트짜리 `DataObject`** —
*"모르는 포맷 = 벤더"* 규칙에 그대로 걸렸다.

★ [D-75](../27-capture-cases.md)가 *"곁다리 목록은 실기에서 자란다"* 고 적어 둔 그 자리다.
설계 때 예상한 위험이 **첫 실행에서 바로** 터졌다.

#### ③ 그런데 고쳐도 여전히 리치였다 — `CF_OEMTEXT`

곁다리를 채웠는데도 안 됐다. ⚠️ **`CF_OEMTEXT`가 평문 목록에 없었다.**
Windows는 텍스트를 `CF_UNICODETEXT`·`CF_TEXT`·`CF_OEMTEXT` **셋으로 함께** 올리는데
셋째를 몰랐으니 벤더로 세어졌다.

#### ④ ★ "벤더면 무조건 리치"가 틀렸다

.NET `System.Drawing.Bitmap`으로 복사한 **순수 그림**이 `RichText`로 찍혔다.

설계 초안은 *"PPT 도형에도 `CF_DIB`가 있으니 벤더가 비트맵보다 먼저"* 였다. 맞는 말이지만
**너무 넓었다** — 그림 전용 벤더까지 리치로 끌고 갔다.

★ **글이 하나도 없는데 "서식 있는 글"이라고 하면 거짓말이다.** 갈래를 하나 넣었다:

```
③ 벤더가 있다
     ├ 평문이 함께 있다  → RichText   (PPT 도형 · Excel 범위)
     ├ 아니고 비트맵     → Image      ★ 그림 전용 벤더
     └ 둘 다 없다        → RichText   (순수 개체)
```

### 4. 설계가 코드를 만나며 바뀐 것

| # | 무엇 | 왜 |
|:--:|---|---|
| **1** | `ClipSnapshot.reps`가 `Representation` → **`RawRep`** | ★ 감시 계층은 `blob_id`(암호문 해시)를 **만들 수 없다** — 키는 저장 계층이 갖는다. **모르는 것을 채우게 만들지 않는다** |
| **2** | `capture`가 **`RepInfo` 제네릭**으로 | 판정에 필요한 건 **이름과 크기뿐**이다. 그러면 `RawRep`도 `Representation`도 그대로 들어간다 |
| **3** | `Captured.reps` → **`keep: Vec<usize>`** | 20MB짜리를 판정 한 번에 한 벌 더 만들 이유가 없다 |
| **4** | `PreviewMissing::ThumbMissing` 신설 | 썸네일이 아직 없는 것을 `TooLarge`로 뭉뚱그리면 **사용자가 원인을 잘못 짚는다** |

### 5. `watch` 명령 — 진단이 제품과 **같은 함수**를 쓴다

★ 진단용으로 따로 판정하지 않는다. `watch`는 실제 저장 경로가 쓸 `capture()`를 그대로 부른다 —
**여기서 맞게 보이면 제품에서도 맞다.** 버려진 표현에는 `✂`를 찍어 **조용히 사라지지 않게** 했다.

## 2차 — ⚠️ Retina에서 **글자만 작아져 있었다** · macOS K-1 통과

### 1. 증상 — 레이아웃은 2배, 글자는 1배

사용자가 mac 설정 창 스크린샷을 보내 왔다. 행 높이·사이드바 폭·여백은 정상인데
**글자만 깨알**이었다. *"beep 때도 겪었던 화면 비율 문제"* 라는 제보와 함께.

### 2. 원인 — 한 줄이 빠져 있었다

`RasterCtx`는 배율을 **글자 크기에 곱해서** 그린다. 그런데 호스트가 그 값을 안 넘겼다.

```rust
let mut dc = RasterCtx::new(&mut gfx, &self.font);   // 배율이 기본 1.0으로 남는다
```

위젯에는 `set_scale(2.0)`을 줬으니 **레이아웃만 2배**가 됐다.

`nexa-beep`를 확인하니 같은 자리에서 **`.with_scale(entry.scale)`를 부르고 있었다**(`app.rs:14055`).
이식하면서 그 한 줄이 빠진 것이다.

★ **Windows(배율 1.0)에서는 우연히 맞아 보인다.** 그래서 한쪽 OS에서만 조용히 틀렸고,
mac에서 실제로 띄워 보기 전까지 아무도 몰랐다. 1차의 *"OS 분기 코드는 그 OS에서
한 번은 빌드되기 전까지 '작성됨'이지 '됨'이 아니다"* 와 같은 이야기다 —
**빌드를 넘어 화면까지** 그렇다.

### 3. 조치 — 테스트가 아니라 **구조**로

```rust
pub fn new(surface: &mut Surface, font: &Font, scale: f32) -> Self
```

배율을 **필수 인자**로 승격했다. 빌더 옵션(`with_scale`)이면 또 빠뜨릴 수 있지만
**인자는 컴파일러가 강제**한다. `with_scale`은 없앴다 — 방법이 둘이면 하나를 잊는다.

⚠️ 테스트로 막을 수도 있었지만 *"렌더 결과가 배율에 맞는가"* 는 픽셀을 봐야 하는 검사다.
**애초에 못 쓰게 만드는 쪽**이 싸고 확실하다.

### 4. macOS K-1 통과 (사용자 실기)

```
cargo run -p nexa-clip -- spike-paste --wait 8
→ 손쉬운 사용에 iTerm 추가 후 Sublime Text 붙여넣기 성공
```

★ **Windows와 달리 복원 경로까지 실제로 돌았다.** mac은 스파이크를 띄운 터미널이
프런트모스트였다가 대상 앱으로 넘어가므로 `NSRunningApplication` 활성화가
**우회 없이 정상 경로로** 실행된다(Windows에서 `[3] 포커스 탈취: 실패` 로 건너뛴 구간).

⚠️ **권한 주체가 우리 바이너리가 아니라 터미널이다.** `cargo run`으로 돌리면
iTerm이 권한을 갖는다. 배포본(`.app` 번들)에서는 **번들 자체를 손쉬운 사용에 추가**해야 하고
그때 권한이 다시 물어진다 — **개발 중 통과가 배포본 통과를 뜻하지 않는다**(→ T-9d).

## 1차 — macOS 빌드가 깨져 있었다 · 설정 읽기 mac 실기 확인

### 1. ⚠️ `nclip-plat`이 macOS에서 한 번도 컴파일된 적이 없었다

`cargo build --workspace`가 mac에서 **E0133 × 13**으로 죽었다. 위치는 K-1 스파이크(16차 · `dddd478`)의
mac 전용 `paste::imp::appkit` — `cls`·`sel`·`send0`·`send0_i32`·`send1_bool`.

원인은 단순하다. `nclip-plat/src/lib.rs`가 **`#![forbid(unsafe_op_in_unsafe_fn)]`** 인데, 저 다섯 `unsafe fn`이
본문에서 `unsafe {}` 블록 없이 FFI를 호출했다. Windows 세션에서 작성돼 **`cfg(target_os = "macos")` 안쪽은 컴파일러가
본 적이 없었다.** CI 매트릭스에 `macos-latest`가 있으니([18 §6](../18-build-and-test.md)) 그 잡도 빨간 상태였을 것이다.

수정은 본문을 `unsafe { … }`로 감싼 것뿐 + `unreachable_pub` 경고 2개(`pub` → `pub(super)`).
★ **교훈** — OS 분기 코드는 **그 OS에서 한 번은 빌드**되기 전까지 "작성됨"이지 "됨"이 아니다.
[21](../21-manual-test.md)의 ☐/⏳ 구분과 같은 얘기다.

### 2. T-12c 설정 읽기 — macOS ✅

17차의 점검 화면 수정이 mac에서도 그대로 맞는지, 저장본 두 상태로 돌렸다.

| 상태 | `settings` | view | theme | max items | tray |
|---|---|---|---|---|---|
| 파일 없음 | `target/debug/data/settings.cfg (아직 없음 — 기본값)` | Compact | system | 1000 | 8 |
| 저장본 | `… (저장본 사용)` | **Rich** | **dark** | **2500** (후보에 없는 직접 입력값) | **15** |

포터블 우선([DR-33](../10-decision-record.md))이 mac에서도 실행 파일 옆 `data/`를 골랐다 — `target/debug`는
`is_replaced_on_upgrade`에 걸리지 않는다(맞다 — `.app` 번들도 Homebrew keg도 아니다).

`nexa-clip settings`도 뜬다 — `폰트: Apple SD Gothic Neo · 설정 항목 21개`. 창 조작(값 변경 → 재시작 · 미지 키
보존 · 숫자 표시 · hover 페이드)은 **사람 손이 필요**해 [21](../21-manual-test.md) ⏳로 남긴다.

`paste inject : ok (mac-cgevent)` — K-1 mac 검증([21 §2-4](../21-manual-test.md))도 사람 손이 필요하다
(손쉬운 사용 권한 + 대상 앱 클릭).

235 테스트 · fmt · clippy `-D warnings` 클린 — **이번엔 mac에서**.
