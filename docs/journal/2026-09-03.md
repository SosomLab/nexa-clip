## 5차 — ★ 결함: Firefox 한글 → `\uXXXX` · 터미널 → `\E2\9E\9C` — charset 없는 `text/plain`을 먼저 집음

사용자 실기 두 건: Firefox에서 한글 복사 → `\ub274\uc2a4…` · GNOME 터미널 프롬프트(➜ ✗) 복사 → `\E2\9E\9C`.

**진단**: `peek --diag`(원시 TARGETS 진단 신설)로 Mutter XWayland 브리지 순서 확인 —
`["TARGETS","TIMESTAMP","MULTIPLE","text/plain","UTF8_STRING","STRING","TEXT","text/plain;charset=utf-8"]`.
`read_snapshot_with`는 텍스트 atom을 `text/plain` 하나로 정규화하며 **TARGETS 순서의 첫 것**만 담았고, 그게
charset 없는 `text/plain`이었다. GTK `selection_set_text_plain`은 bare `text/plain`을 **ASCII**로 변환하고
glib `g_convert_with_fallback`(fallback NULL)이 비ASCII를 `\uXXXX`로 쓴다(RFC 2046 text/plain 기본 charset = US-ASCII).
VTE 쪽 `\E2\9E\9C`는 같은 타깃의 바이트 이스케이프 변형. 즉 **원본 앱도 브리지도 정상 — 우리가 잘못된 타깃을 골랐다.**

**조치** — `watch_linux.rs`: `text_rank()` 신설 — `text/plain;charset=utf-8`(0) → `UTF8_STRING`(1) → `text/plain`(2) →
`TEXT`(3) → `STRING`(4, Latin-1). `read_order()`로 텍스트 계열만 순위 정렬(나머지는 TARGETS 순서 유지) ·
순위 첫 타깃 읽기 실패 시 다음 순위로 물러남(지연 제공 대비). 단위 테스트(관찰된 실제 순서 그대로) ✓ · clippy ✓.
도구 파이프 폴백(xclip/wl-paste)도 같은 함수를 타므로 함께 해소.

**진행사항 최신화·병합**(사용자 요청): STATUS 2~5차 블록 · TODO(T-14 병합 표기 · **T-15d 신설** — 단축키 후 검색창 `v` 연타, 사용자 실기) ·
BRANCHES(11 커밋) · MILESTONES(감시 3-OS ✅). 워크스페이스 테스트 403 ✓ · clippy 0 → `feat/linux-clipboard-native` → main `--no-ff` 병합 · push.
병합 후 main 직접(docs만): **T-14i**(Linux 내재화 실기 가이드 미수행 — 메인창·팝업 점검만 진행 중) ·
**T-18g**(팝업 검색 `push` 결과 없음 · 등재 당시 T-18c 오기 — 부수: `➜`·`✗` 두부 렌더) 등재 → push.

**실증**: GTK3-X11 직접 소유(UTF8_STRING 선두) ✓ 한글·➜·✗ 정상. Mutter 브리지 순서는 헤드리스 Wayland 앱이
입력 serial 없이 셀렉션을 못 잡아(wl-copy 미설치) **사용자 재복사로 검증 ⏳**. 기존에 잡힌 이스케이프 항목은 삭제 대상.

## 4차 — ★ 결함: 로그인 자동 시작이 배너만 찍고 종료 — 등록 명령에 `tray` 인자 누락(3-OS)

사용자 실기 "자동 시작이 되지 않았어". journal(`journalctl --user`) 확인 — `nexa-clip.desktop[2812]`가 00:46:15에
실행되긴 했으나 **환경 점검 배너(`Nexa Clip v0.1.0 · target: linux …`)만 찍고 끝남**. `~/.config/autostart/nexa-clip.desktop`의
`Exec`가 바이너리 경로만 있고 `tray`가 없었다.

**원인**: `nclip_plat::autostart`는 beep `nbeep-plat/autostart.rs` 무수정 이식 — beep은 **무인수 = 상주**지만 clip은
**무인수 = `status()`(환경 점검)** 이라 이식 가정이 깨졌다. Linux `.desktop`만이 아니라 **Windows Run 값 · macOS plist
`ProgramArguments`도 동일**(3-OS 잠복 결함). 런처 `.desktop`(`install_launcher`)만 `tray`를 붙이고 있었다.

**조치** — `autostart.rs`: `pub const TRAY_ARG = "tray"` 신설 · Linux `Exec="…" tray` · Windows `run_value()` 분리(`"…" tray`) ·
macOS `<string>tray</string>` 추가 · 모듈 문서에 beep과의 차이 명기. 테스트 3곳 갱신 + `run_value` 테스트 신설(7/7 ✓).
`scripts/dev-restart.sh`로 재시작 → `boot_sync`가 `.desktop`을 현재 형태로 재기록한 것 확인 ✓(`Exec="…/nexa-clip" tray`).
다음 로그인에서 실기 검증 필요(☐).

**추가 검증(로그아웃 없이)** — 기존 인스턴스 종료 후 `gio launch ~/.config/autostart/nexa-clip.desktop`(GNOME과 같은 desktop 실행기)로
재현 → `tray` 진입 · 감시/트레이/주입/단축키 전부 ok ✓. `desktop-file-validate` 통과 · appindicator 확장·StatusNotifierWatcher 상주 확인.
**부수 발견**: 단일 인스턴스 가드 없음 — 자동 시작 상주 중 재실행하면 감시 2중·트레이 2개 → **T-12e4** 등재(사용자 요청).
사용자 실기: ★ **최상위 고정 동작 확인**(09-02 19차 libxkbcommon-x11 선결 → 이번 세션 실동작).

## 3차 — 실기 판정: "터미널에 붙여넣기 안 됨" = 결함 아님 — VTE Ctrl+V 관례

사용자 실기(B1 변형 — 대상 = 터미널): 팝업 선택 → 로그 `재적재 … 표현 4개 게시` · `붙여넣기: 포커스 복원 + 키 주입 ok`,
그러나 터미널에 안 붙음.

**교차 실증**: `peek`(내재 읽기)로 회수 — 재적재 항목이 4개 표현 그대로 서빙 중 ✓. 즉 수집→재적재(내재 서빙)→주입까지
전부 정상이고, **GNOME 터미널(VTE)이 Ctrl+V를 붙여넣기로 받지 않는 것**(터미널 관례 = Ctrl+Shift+V · Ctrl+V는 리터럴)이 원인.
Windows 터미널은 Ctrl+V를 받으므로 Windows 동등성 결함도 아니다.

- 즉시 우회: 터미널에서는 선택 후 **Ctrl+Shift+V 수동**(클립보드엔 이미 실려 있다)
- 본편 방향(신규 T-15c): **대상 앱별 주입 조합** — X11/XWayland 창은 `WM_CLASS`로 터미널 감지 가능 ·
  네이티브 Wayland 창은 포털이 대상 정체를 안 주므로 **감지 불가 판정**(정직 강등 · 문서 안내)
- 부수: `scripts/dev-restart.sh` 신설(빌드→종료→재시작 · `--diag`) — 사용자 요청
